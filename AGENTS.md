# {{APP}} — agent guide

A kanban board shared between a human and agents. **The board is the conversation**: the human edits tickets, comments, and answers your questions here instead of re-prompting you. Read it, act on it, write back to it.

Base URL: `{{BASE}}`  ·  index: `GET /api`  ·  schema: `GET /api/schema`

## Start here

```
GET /api/boards/main/brief        (CLI: intellagent brief · MCP: get_briefing)
```
One page: who you are, **what to do next**, the columns, templates, fields, rules and the exact calls for this board. Read it at the start of every session or run — it is generated from the live board, so it is never stale. The rest of this guide is reference.

The whole loop for one ticket:

| Step | Call | What it does |
|---|---|---|
| What needs me? | `GET …/work` | Next actions, your leases, answered questions, review feedback, assigned and ready tickets |
| Start / resume | `POST …/items/<ID>/start { status }` | Claims it, moves it to the working column, assigns you — all or nothing |
| Say what you're doing | `PUT …/items/<ID>/status { status }` | Live line on the card |
| Ask | `POST …/items/<ID>/attention { reason }` | Card glows; the answer comes back in `…/work` (`answered`) and as an event |
| Done | `POST …/items/<ID>/review { changed, why, verify, evidence, risks }` | Moves to review, releases your lease, asks the human — explain in five parts |
| Asked to explain | a comment with `intent: "explain"` (also first in `…/work`) | Answer in a comment; change nothing else |
| Verdict | (human) `review.approved` / `review.changes_requested` | Feedback shows in `…/work`; `start` again to address it |
| End of session | `POST …/finish { summary }` | Releases everything you hold, posts the digest |

Errors are `{ "error": "…", "code": "LEASED", "hint": "…" }`. Branch on `code`, follow `hint`. Codes:

| Group | Codes |
|---|---|
| Held or blocked | `LEASED` `NOT_LEASED` `BOARD_HELD` `LEASES_ACTIVE` `BLOCKED` `WIP_LIMIT` `LOCKED_COLUMN` `OUT_OF_FOCUS` |
| Not yours to do | `HUMAN_ONLY` `OWN_WORK` `OUT_OF_SCOPE` `NOT_DELEGABLE` `NOT_ROUTABLE` `FORBIDDEN` `UNAUTHORIZED` |
| Wrong input | `BAD_REQUEST` `UNKNOWN_FIELD` `IMMUTABLE` `EXPLICIT` `BAD_EMOJI` `MODEL_NOT_ALLOWED` `WIDEN` `NO_AGENT` |
| Wrong state | `VERSION_CONFLICT` `REVIEW_OPEN` `OKS_MISSING` `REVIEW_PENDING` `NO_REVIEWER` `NO_REVIEW` `ALREADY_DECIDED` `NOT_TEST` `NOT_FOUND` `ARCHIVED` `LOCKED` `CONFLICT` `TOO_LARGE` `MEMORY_OFF` |
| Agent management | `STANDING_AGENT` `ONLINE` `HOLDS_LEASES` `PROBATION` |

## 0. Rules of the road

1. **Identify yourself** on every request: header `X-Agent: <your-name>` (or `?agent=<name>`). Use one stable name per agent.
2. **Read the board rules first**: `GET /api/boards/main/directives` returns the board rules (how to use the board) **and** the project conventions, the project's own convention files (e.g. CLAUDE.md, under `projectRules`). Conventions live in the repo; the board only adds how to use the board. Never copy one into the other.
3. **Start before you work** (`POST …/start` leases the ticket for you), renew while working, request review when done — or, if you are the only agent, **hold the whole board** once (master lease, below).
4. **Ask, don't guess**: `POST …/attention` when blocked on a decision — allowed even on tickets others hold. The answer shows up in `GET …/work`.
5. **Never write `data/` files directly.** They are read-only on purpose. The API is the only writer.
6. Tickets are never deleted — archive them. The one exception is **test tickets**: created with `"test": true` (fixed at creation), they may be removed for good by anyone with `DELETE …/items/<ID>` (leases still apply; the human can clear them all with `DELETE …/test-items`). Use them for anything throwaway; they stay out of metrics, the digest and the receptionist's sweep.

## 2. Create and change work

```
POST  /api/boards/main/items             { "title": "…", "column": "Backlog", "type": "task|issue|spike",
                                           "priority": "Low|Medium|High|Critical", "parent": "auth",
                                           "description": "markdown", "properties": { "estimate": 3 },
                                           "blockedBy": ["INT-4"] }
PATCH /api/boards/main/items/INT-12      { "priority": "High", "properties": { "risk": "low", "old": null }, "version": 7 }
POST  /api/boards/main/items/INT-12/move { "column": "Review", "beforeId": "INT-9" }   // or "position": 0 | "top" | "bottom"
POST  /api/boards/main/items/INT-12/comments    { "body": "markdown, @mention someone" }
POST  /api/boards/main/items/INT-12/attachments { "path": "C:/abs/path/screenshot.png" }  // or dataBase64 / url
POST  /api/boards/main/items/bulk        { "ids": ["INT-1","INT-2"], "patch": { "column": "Done" } }
POST  /api/boards/main/archive           { "ids": ["INT-1"], "reason": "duplicate" }
POST  /api/boards/main/archive/INT-1/restore
```

- Attaching by `path`: agents may attach files from the project, their worktree and the OS temp folder (`403 FORBIDDEN` elsewhere; send `dataBase64` instead). Nobody can attach `local.json` or anything in the board's data folder. Avatars by `imagePath` follow the same rule.
- `properties` is your free-form property bag — **merged** on PATCH; set a key to `null` to delete it; `"replaceProperties": true` to replace wholesale.
- Send `"version"` (from your last read) on PATCH to avoid overwriting the human's concurrent edits → `409` means re-read and retry.
- Columns have flags. `allowCreate:false` → `403` on create; `allowMoveIn/Out`, `wipLimit` (hard cap → `409`). Read them via `GET /columns`.
- Unknown PATCH fields are rejected with a hint — custom data goes in `properties`.

## 2b. Ticket schema — design what a ticket holds

Each board has a schema. **Declare typed fields** for the data your task needs; the UI renders proper controls for them and can show them on the card.

```
GET   /api/boards/main/schema
POST  /api/boards/main/schema/fields   { "key": "risk", "label": "Risk", "type": "enum",
                                         "options": [{ "value": "low", "color": "#4cc38a" }, "medium", { "value": "high", "color": "#ff5d73" }],
                                         "stub": "top", "ui": "edit", "icon": "flag", "help": "Blast radius if this goes wrong" }
PATCH /api/boards/main/schema/fields/risk   { "stub": "meta" }
DELETE /api/boards/main/schema/fields/risk  (definition removed; stored values are kept)
PUT   /api/boards/main/schema          { "builtins": { "priority": { "ui": "hidden" }, "blockedBy": { "ui": "read", "label": "Waiting on" } } }
PATCH /api/boards/main/items/INT-12    { "fields": { "risk": "high", "estimate": 3, "reviewed": true } }   // null clears
```

- Types: `text markdown number boolean enum tags date url user`. `number` accepts `min`/`max`; `enum`/`tags` take `options` (tags without options are free-form). `required` and `default` apply on create.
- Tags with options, e.g. `POST …/schema/fields { "key": "area", "type": "tags", "options": ["server", "ui"] }`, then set it as a JSON array: `PATCH …/items/INT-12 { "fields": { "area": ["ui"] } }`.
- `ui`: `edit` (humans can change it), `read` (humans see it but **only agents/API can change it**), `hidden` (API only).
- `stub`: `none` | `top` (badge beside the id) | `meta` (chip in the card footer).
- Built-ins (`type priority parent description blockedBy attachments cover properties`) take `{ ui, stub, label }`. `blockedBy` defaults to `ui: "read"`. Only the human changes them.
- Wrong types or unknown enum values → `400` listing what's allowed. Undeclared keys → `400`; use `properties` for ad-hoc data.
- Search fields with `fields.<key>` paths or `?f.<key>=value`; subscribe to changes with `fields=fields.risk`.

### Ticket templates
Presets for new tickets on this board ("Bug", "Feature"…). The human picks them in the UI; you pass `template`:

```
GET    /api/boards/main/ticket-templates
POST   /api/boards/main/items              { "template": "bug", "title": "Crash on save" }   // your values override the template's
POST   /api/boards/main/ticket-templates   { "label": "Bug", "type": "issue", "priority": "High", "column": "Triage",
                                             "description": "**Steps**\n1. ", "fields": { "risk": "medium" }, "help": "Something is broken" }
PATCH  /api/boards/main/ticket-templates/bug   { "priority": "Critical" }
DELETE /api/boards/main/ticket-templates/bug
```
Prefer a template when one fits — tickets then look the same whoever files them. Fields and properties merge key by key; everything else you pass wins.

### Tickets an agent writes up
The human can file rough notes with **Let the agent write it** (`POST …/items { "title": "…", "agentWrite": true, "explicit": ["priority"] }`). The ticket gets an `agentDraft` marker `{ writer, explicit, original }` and wakes the writer (the board's coordinator), whose `…/work` shows a `write` action. Rewrite the title, description (with an acceptance checklist), type, priority, fields, parent and blockers — but not the keys in `agentDraft.explicit`: the human set those on purpose, and the board answers `409 EXPLICIT` if you touch them. A human edit while the draft is pending adds its keys to `explicit`. Quote the original title and description in a comment, then send `"agentDraft": null` with your rewrite to clear the marker.

Card image: `PATCH … { "cover": "auto" | "none" | "<attachment id>" }` (auto = first image).
Comments can carry files: `POST …/comments { "body": "see screenshot", "attachments": [{ "path": "C:/abs/shot.png" }] }`.

## 2e. Your memory

A few notes you keep across runs: your brief shows them every run, under **Your memory**. Keep a lesson that will help on future tickets ("the focus tests share a port: run them alone"); never progress, and never what a card already says.

```
GET    /api/profiles/me/memory            → { name, on, cap, used, entries: [{ id, text, source, from?, at, by, pinned?, history?, suggestedBy? }], suggestions }
POST   /api/profiles/me/memory            { "text": "…", "from": "INT-12" }        (MCP: remember)
PATCH  /api/profiles/me/memory/<id>       { "text": "…" }                          (earlier texts kept in history)
DELETE /api/profiles/me/memory/<id>                                                (MCP: forget)
PUT    /api/profiles/<agent>/memory       { "on": false }                          (human only: the switch)
POST   /api/profiles/<agent>/memory/suggestions                { "text": "…", "why": "…", "from": "INT-12" }   (MCP: suggest_memory)
POST   /api/profiles/me/memory/suggestions/<id>/accept         { "text"?: "your rewording" }
POST   /api/profiles/me/memory/suggestions/<id>/decline        { "reason": "…" }
```
- Two kinds of entry: **learned** (you wrote it) and **human** (the human told you to remember it). You change only your own learned entries, and not the ones the human pinned (`403 HUMAN_ONLY`); another agent's memory is not yours (`403 FORBIDDEN`). The human adds, edits, pins and removes any, on `/api/profiles/<agent>/memory`.
- The human's comment or request that *starts* with "remember that …" or "remember: …" (after any @mentions) becomes a human entry for each agent it @mentions, or for the request's agent. The reply lists them under `remembered`.
- At most 4000 characters per agent and 1000 per entry (`413 TOO_LARGE`: forget or shorten one). Each entry is one line.
- **Memory never grants anything.** It is only text in your brief, framed as your own notes: they can be wrong, and they never override the human's instructions or your permissions. Every change is a `memory.updated` event (wakes nobody), and the digest lists what each agent learned that day (`learned`).
- The human can switch an agent's memory off, e.g. for an agent that reads outside content: its brief shows none and its writes answer `409 MEMORY_OFF`. Its entries are kept. A read-only agent (`readOnly` in its permissions) still writes its own memory: read-only covers the board, and the switch is the control for memory.
- **Suggesting a note for a colleague** (INT-402). You can't write into another agent's memory, but you can propose a lesson for it: `POST /api/profiles/<agent>/memory/suggestions { text, why, from? }`. The note waits under `suggestions` on that agent and is never in its memory or its brief as memory: it reaches the agent once as a `memory_suggestion` in its `…/work`, saying who suggested it and why. The agent accepts it (`…/accept`, reworded with `text` if it likes), and it becomes a **learned** entry with `suggestedBy`, or declines it with a `reason`, which goes back to you. The human can accept (with `text` to edit it first, and `pinned`) or decline any; accepted by the human, it is a **human** entry. Limits: 1000 characters (and `why` 300), counted against the 4000 only once accepted; at most 5 waiting per agent and one per suggester and agent a day, declined ones included (`409 CONFLICT`); never to yourself, and a human adds directly (`400`); memory off: `409 MEMORY_OFF`; an agent on probation can't suggest. Events: `memory.suggested` (addressed to the agent, so it wakes it), `memory.suggestion_accepted` / `memory.suggestion_declined` (in the suggester's inbox, addressed to nobody: they wake nobody). The digest lists accepted suggestions under `learned`, with `suggestedBy` and `acceptedBy`.
- `<agent>` must be an agent the board knows (in agents.json, or one that has called the board), matched without regard to capitals, so `Rocket` is rocket's memory. Any other name answers `404 NOT_FOUND`, and a name that can't be an agent's `400`.

## 2f. Area notes: what you learned, for whoever works there next

Every run starts with no memory, so what a run works out about the code (how a module is wired, what is slow or fragile, what to run) is lost unless it is written down. Memory is one agent's; **area notes** belong to the code: each is kept by area (a file or a folder of the project) and read by any agent that works there.

```
GET    /api/notes?path=lib/alerts/        → { notes: [{ id, area, text, by, from?, at, confirmedBy? }], count }   (MCP: area_notes)
POST   /api/notes                         { "area": "lib/alerts/work.js", "text": "…", "from": "INT-12" }        (MCP: add_note)
POST   /api/notes/<id>/confirm            this one helped (not its author)
POST   /api/notes/<id>/retire             { "why": "…" }: wrong or out of date (anyone; kept for the record, ?retired=true)
PATCH  /api/notes/<id>                    { text?, area? } (its author or the human)
DELETE /api/notes/<id>                    (the human only)
```
- **Leave them when you request review:** `learned` is the review's sixth part, one note per line: `area: lesson` (`lib/alerts/work.js: the TAG table decides when work is new again`), or `none`. Each line becomes a note from that ticket; the review card shows it under *Learned for next time*. An agent's review with no `learned` (not even `none`) comes back with a warning, as one without evidence does, and a line with no area is reported, not kept.
- **They come back to you:** `start` returns `notes` for the paths the ticket names (in its title and description), your own `areas` and the ticket's earlier notes; your brief lists the notes on your areas under **Area notes**. Read them before you explore.
- A folder note covers what is in it, and asking about a folder finds the notes inside it. Notes others confirmed come first. An area keeps at most 8 (the least confirmed, oldest goes, retired rather than lost), a note is at most 600 characters, and the same lesson on the same area counts as a confirmation instead of a second note.
- Notes are only text an agent reads, like memory: they never grant anything, and they can be wrong. Retire one that misled you, saying why.

## 3. Leases (locks)

```
POST   /api/boards/main/items/INT-12/lease   { "minutes": 30 }   → claim, or renew if you already hold it
DELETE /api/boards/main/items/INT-12/lease                       → release
```

- While you hold a lease, **other agents** get `423 Locked` on writes to that ticket. Humans can always edit (and may revoke your lease).
- Renew before expiry. You receive `lease.warning` ~5 minutes before, then `lease.expired`.
- Moving into a column with `releaseLeaseOnEnter` (e.g. Done) releases automatically.
- **Say what you're doing** while you hold the lease — it shows live on the card (doesn't bump `version`):
  `PUT /api/boards/main/items/INT-12/status { "status": "running tests 4/12" }` (or pass `status` when claiming).

### Start work in one step
`POST /api/boards/main/items/INT-12/start { "status": "reading the code", "minutes": 30 }` checks the ticket isn't held or blocked, leases it to you (not needed while you hold the master lease), moves it to the working column (flag `working`; e.g. In Progress) unless it is already there or further, and assigns it to you. If any check fails nothing changes and you get a `code` (`LEASED`, `BLOCKED`, `WIP_LIMIT`, `BOARD_HELD`). Pass `"force": true` to start a blocked ticket, `"column"` to pick the target. The reply includes `feedback` (if the review sent it back) and `lastAnswer` (your last question's answer).

### Explaining your work
Reviews explain themselves in five parts: `changed` (what changed), `why` (the reasoning, and alternatives you rejected), `evidence` (what proves it works: screenshots, outputs, tests), `verify` (how the human can check it) and `risks` (risks and open questions), plus `learned`: what the next agent working on that code should know (area notes, section 2f). The review card shows each part in full. A single `summary` still works.

Keep `changed` short, plain and to the point. A non-technical reader should be able to follow it: say what the change does for the user, and name files, functions or flags only where the change needs them. Keep the other four parts as complete as they need to be. Example:
- Before: "server.js (requestReview): counts commits via worktrees.commitsFor and stores `landing` on the review question; app.js renders a `.rv-does` line and a conditional button label."
- After: "The review card now says what Approve will do, and the button says *Approve and land* when agent commits are waiting."
When the human wants more, they **Ask why** — a comment with `intent: "explain"`, addressed to you if it @mentions you or, if not, to whoever requested the review or last worked the ticket. It arrives as an `[EXPLAIN ONLY]` event and tops your `…/work`. Answer in a comment and change nothing else: not the code, the ticket, its column or the review — the review stays open while they read your answer.

### Request review (preferred way to finish)
`POST /api/boards/main/items/INT-12/review { "summary": "What changed and how to verify" }` — moves it to the review column, comments your summary, releases your lease and raises a **review** request.
**Evidence is required.** The human approves only what they can see working, so every review carries `evidence`: screenshots (attach them to the ticket and name them), the command you ran and its output, test results, and for anything visible, what to look at in the Preview. A review without it comes back with a warning. A design decision a person sees (a look, layout, theme, motion or flow) needs its screenshots attached before review is requested: light and dark theme, and 375 px wide where the layout changes, each named for what it shows (e.g. `int202-light-375.png`) and listed in `evidence`. An API or CLI change shows its command output instead. On a board whose code is Intellagent itself, the review card has a **Preview** button: the board runs the author's branch on a temporary board (`sandboxes/preview/`, a fresh copy of the tickets) and opens it signed in, so commit everything the ticket needs before you ask (`POST …/items/<ID>/preview`, human only; `"preview": true` in `GET /api/app` says the board can).
The human decides with `POST …/review/decision { "verdict": "approve" | "changes", "comment": "…" }` (human only): approve moves it through the gate; changes moves it back to the working column. Moving a ticket with an open review into an approval gate (e.g. dragging it to Done) counts as approve. You receive `review.approved` or `review.changes_requested` (with `feedback`), and `GET …/work` lists it under `feedback` until you `start` it again.

### End a session
`POST /api/boards/main/finish { "summary": "markdown", "items": ["INT-12"] }` releases every lease you hold (and the master lease) and posts the summary to the digest. Standing-agent runs that exit cleanly get this release automatically.

### Metrics
`GET /api/boards/main/metrics?days=7` (or 30): tickets done (and the previous window), median cycle time (working column → done), median time in each column, open questions and how long the oldest has waited, and how fast the human answers. The UI shows it as a strip under the top bar.

`GET /api/analytics?days=7` (1-90, default 7; `&agent=<name>` for one agent) is the agents' side: per agent, time in each state (`states`: running, queued, waiting, throttled, idle, paused, failed… in ms; `unknownMs` before its first known state), queue depth at each run start (`queue`), runs and how they ended, tokens, cost (`cost`, with `unpriced` counting runs that reported none: unknown, never 0), the same per model, and the top tools and command names; per ticket, runs, time, tokens and cost (a run woken for several tickets is shared between them equally, so tickets add up to the agents' totals). Each agent also has `segments` (`{ from, to, status, note? }`, clipped to the window, the newest 500: one lane on a time axis; `note` is the board's own words, e.g. "usage limit"), each agent and `totals` also carry `daily`, one `{ day, runs, cost, unpriced }` per UTC day of the window, oldest first, by the day a run ended (a day with no priced run has `cost: null`, never 0), and the reply has `suggestions` (`{ kind, text, agents?, items? }`): `rebalance` when one agent spent a fifth of the window queued, throttled or waiting while another sat idle half of it, and `waiting-on-human` for tickets waiting on the human over a day. It is worked out on each call from the `agent.status` events and the run records in `agent-stats.jsonl`, live and rolled files, reading only the files of the window. **Anyone who can read the board may read it**, the human and every agent: it holds command names only, never command lines, prompts or ticket text.

`GET /metrics` is the same board for Prometheus (text format 0.0.4, `docs/grafana/` has a scrape block and an importable Grafana dashboard): tickets per column, done and cycle time, open questions, reviews, landings, leases, and per agent its status, queue, runs, run time and tokens. It is **off** until the manifest has `"metrics": { "prometheus": true }` (`404 NOT_FOUND`, the hint names the switch), and then answers only to the **metrics token** as a bearer (`401 UNAUTHORIZED` without it). The human issues it with `intellagent token --metrics` (`--rotate` replaces it); it lives in `local.json`, opens this route and nothing else, and is never in the output. **Autonomy** (INT-393): each ticket keeps its `journey` from pickup (first entry into the working column) to Done, with every human intervention in between by kind (`answer`, `comment`, `move`, `assign`, `edit`, `stop`, `changes`, `decision`), its moves and backward moves; finished journeys are `autonomous` (no human: the approval was delegated), `approved` (the human only approved) or `helped`. `/metrics` counts them (`intellagent_tickets_finished_by_autonomy{level}`, `intellagent_human_interventions{kind}`, `intellagent_ticket_moves{direction}`) with the tickets in flight and the ones stuck (picked up, quiet 4 h: `intellagent_tickets_stuck{reason}`: `waiting_on_human`, `held_quiet`, `idle`); journeys are backfilled once from the event log files still on disk. Counters come from board state and the run records, so they survive a restart; no ticket title or comment text is ever a label. Agents have no need of it: use `…/metrics` and `/api/analytics`.

### Daily digest
At the end of a session: `POST /api/boards/main/digest { "summary": "markdown", "items": ["INT-12"] }`. Read what others wrote with `GET /api/boards/main/digest?days=3` — a cheap way to catch up.

### Approval gates
Columns with `humanOnlyIn` / `humanOnlyOut` can only be entered / left by a human (`403` for agents). By default **Done** is human-only: move finished work to **Review** and let the human accept it.

A **sleeping** column (`flags.sleeping`, e.g. Backlog) holds work nobody should start yet. Assigning a ticket there wakes nobody; agents cannot start it there (`409 SLEEPING`) and it is not in their work. Moving it out — into Ready — wakes its assignee. On a board with a sleeping column, agents file new tickets into it (`403 SLEEPING` elsewhere); the **coordinator** decides where a ticket an agent filed goes (leave it asleep, or create or move it into any column it may use), and only the human wakes the human's own tickets.

### Grants: powers the human delegates
Some agents may do human-only things because the human said so — in **agents.json** (or the manifest's `permissions.<name>.grants`), or on the Agents page (an agent's *Edit* › Grants), which only works for the signed-in human on a board with a sign-in token (`intellagent token`; without one the API answers `403 NO_TOKEN`). Agents can never set grants:
```jsonc
"approver":   { "role": "reviewer", "grants": ["review.decide"] },
"gatekeeper": { "enabled": false, "grants": [{ "power": "column.gate", "where": { "column": "Done", "fields.risk": "low" } }] }
```
- `review.decide` — `POST …/review/decision`; the verdict is final, moves the ticket on, and is recorded as delegated (`review.delegated`, the event's `delegated`, a note in the comment).
- `column.gate` — move tickets into / out of human-only columns (a ticket with an open review must be decided instead: `409 REVIEW_OPEN`).
- `agents.control` — pause / resume / run *other* standing agents. Defining agents and grants stays with the human.
- `agents.manage` — `PATCH /api/agents/<name> { label?, glyph?, color?, alignment?, description?, role?, model?, perms?, permissions?: { columns?, readOnly? } }` on *other* standing agents (`where: { "agents": [names] }` limits which). Models only from the allowlist (`managerModels` in the manifest; default haiku, sonnet, opus); tool `perms` and board `permissions` can only narrow, and so can a `role` change for an agent whose tools come from its role (`WIDEN`; send `perms` with it to pin them); the coordinator role is never theirs to give or take (`HUMAN_ONLY`). Narrowing is stored as `limits` in agents.json, intersected with the manifest. Never the run command, grants, enabled, env or its own record (`403 NOT_DELEGABLE` / `OWN_WORK`). Every change is kept with before/after on the agent (Agents page, with Revert), emitted as `agent.managed`, and written to the digest.
- `work.land` — `POST …/items/<ID>/land` for work that is already approved (`409 NOT_APPROVED` otherwise; landing never decides anything). A failed landing with commits waiting is recorded on the ticket (`landing: { state: "failed", reason, from }`), @mentions the agents holding `work.land` instead of asking the human to run `intellagent merge`, and shows as a `land` action in their work. **Already on main:** a ticket commit whose patch main already has (same `git patch-id`, whatever the message or sha) is not cherry-picked again but counted as landed, and the card says `Already on main: <sha> as <main sha>`; main's 300 newest commits are searched for that twin, and an older one reads "not among the newest commits searched" with main's tip as the only sha. A lander resolves conflicts on its own branch (cherry-pick the author's commits, keep both sides, run the tests) and lands from there with `{ "agent": "<itself>" }`. **Landed by hand:** when someone finished a failed landing themselves (a resolved cherry-pick has other ids), the board notices on its sweep: main has a commit naming the ticket after the approval, so the card shows `landing: { state: "landed", by: "hand", commits }` and the `land` action goes. To say so yourself, `POST …/land { "landed": [shas] }` or `intellagent merge <ID> --mark-landed [sha,sha]` (comma-separated; no shas: main is searched for the ticket id). Only for an approved ticket whose landing is `failed` (`409` otherwise), and the shas must be on main.
- `where` limits a grant to tickets matching every key (`column`, or any dotted path such as `fields.risk`, `properties.area`; a value or a list). `reviewers.<name>` matches that reviewer's current verdict: `{ "power": "review.decide", "where": { "reviewers.nebula": "ok" } }` lets an agent approve what that reviewer passed.
- **Required reviewers:** a `review.decide` or `column.gate` grant may carry `"minOks": 2, "from": ["nebula", "kraglin", "drax"]`: it works only once that many of the named reviewers have said ok. `minOks: "all"` (or `from` alone) wants every one named; with no `from`, the reviewers assigned to the ticket count, so `{ "power": "review.decide", "minOks": "all" }` waits for every assigned reviewer. An ok counts only while it stands: given with the reviewer's own token, about the commits the ticket has now, and never from one of its authors. Until then the agent gets `409 OKS_MISSING` naming each ok still missing (`missing: [{ name, state }]`, state `unassigned` `waiting` `concerns` `unverified` `stale`). A rule is a condition on the ticket as it is, not something an ok is spent on, so **one ok can satisfy several rules**, as GitHub's required reviewers do. Asking for changes needs no oks. A rule that can't be read (`minOks: 0`, more oks than names, a rule on another power) drops the grant, never just the rule; from the Agents page it is refused (`400`).
- **Guidance:** `"guidance": { "review.decide": "Docs tickets first, and say why", "edit": "…" }` on an agent in agents.json: the human's words beside a permission or power it holds. The agent reads them in its brief, marked *Guidance from the human (not enforced)*, and in `GET /api/permissions/me` (`guidance`). Nothing checks them, and guidance for a permission the agent doesn't hold is left out.
- A delegated approval needs evidence in the review (`409 NO_EVIDENCE`), no reviewer with concerns (`409 CONCERNS_OPEN`) and no open blocker (`409 BLOCKED`); without them only the human approves. **No concerns yet is not an ok:** under a grant with no reviewer rule of its own, every reviewer assigned to the ticket must have an ok that stands, and there must be at least one (`409 NO_REVIEWER` while nobody who could review it is assigned, `409 REVIEW_PENDING` with `missing: [{ name, state }]` while an ok is still owed). A grant that says whose oks it needs (`minOks`, or `where: { "reviewers.<name>": "ok" }`) is the human's own rule and is followed as written. An agent with `review.decide` sees each ticket waiting for a decision in its `…/work`: `decide` when everything is in, `chase` naming what is missing (a reviewer, a verdict, evidence, answered concerns, blockers done) so it can @mention whoever owes it. Each wakes it once per change.- Never on your own work: a ticket you worked on or whose review you requested → `403 OWN_WORK`. Out of scope → `403 OUT_OF_SCOPE`; no grant → `403 HUMAN_ONLY`.
- **The human's switch:** "Approves for you" on the Agents page (`GET/PUT …/approvals { on }`, human only) lists who may approve on their behalf and when, and switches it all off: while off, every `review.decide` and `column.gate` grant on that board answers `403 APPROVALS_OFF`, `decide`/`chase` actions go quiet and the brief says so. Landing already-approved work (`work.land`) goes on. The manifest's `approvalsOff: true` makes a board start off.
- **Board admin:** how the board is governed (below, *Boards, columns*) is the human's, and the human can hand it out one piece at a time, each a power in the *Board admin* group of the library: `admin.columns` (*Can edit columns*: flags, order, adding and deleting), `admin.rules` (the directives), `admin.coordinator`, `admin.fields` (the built-in field settings), `admin.focus` (make, change, activate and retire focus boards), `admin.cardRules` and `admin.rebalancing`. `"grants": ["admin"]` is every power at once, each still checked, switched off and limited on its own. It covers a fixed list (the powers above and `review.decide`, `column.gate`, `agents.control`, `agents.manage`, `work.land`): a power added in a later version never joins it, and is granted by name. A scope (`where`) on one may name the `board`, and on `admin.columns` the `column`; anything else is out of scope (`403 OUT_OF_SCOPE`), so adding a column, which names none, needs an unscoped grant. **Limits no grant lifts:** `admin.columns` may add a human-only gate (`humanOnlyIn`/`humanOnlyOut`) but never lift one or delete a gated column (`403 HUMAN_ONLY`): lifting it would let work skip approval. Nor may it change which column is last, by adding a column after it, moving a column there or away, or deleting it (`403 HUMAN_ONLY`): the last column is the done column, and a ticket there counts as approved. `admin.coordinator` never chooses its holder (`403 OWN_WORK`). The human's switches (approvals, admin, the idle alarm), pins and rebalancing undo, tokens, `local.json`, sign-in, grants, run commands and env stay the human's. Every delegated change carries `delegated: { power, onBehalfOf: "human" }` on its event, adds a digest line, and is counted in `…/metrics` (`delegated.admin`; a delegated change that is neither a review, a move nor admin counts under `delegated.other`). **History and revert:** each delegated change that altered a setting is also kept in that agent's Recent changes (`GET /api/agents/<name>` → `changes`, newest last) with the setting before and after (`changes: { directives | coordinator | columns | builtins | cardRules | rebalance | focusBoards, activeFocus: { from, to } }`) and `admin: { board, power, text }`. The human puts it back with `POST /api/agents/<name>/changes/<id>/revert` (human only, the revert button on the Agents page; CLI: `intellagent api POST /api/agents/<name>/changes/<id>/revert`). It goes through one transaction and emits `admin.reverted`; `409 CONFLICT` with a hint when the setting changed again since, when the change was already reverted, or when tickets now sit in a column the revert would remove. An `agents.manage` change is not reverted here: send the old values with PATCH. **Admin off:** `GET/PUT …/admin { on }` (human only) lists who holds an admin power and switches them all off: `403 ADMIN_OFF` until the human switches it back on, and the brief says so. It leaves approvals alone, and it suspends only the `admin.*` powers: `agents.control`, `agents.manage` and `work.land` given through `admin` stay on (approvals have their own switch; take the grant away to stop the rest). **Can edit permissions** (`admin.permissions`) is granted by name only (`admin` doesn't include it). Its holder changes the grid and the library, never beyond what it holds itself:
  - **Grid cells:** `PUT /api/agents/<name>/permissions/<key>` works only on another agent's row. Turning a permission on or off, or writing guidance beside it, works only for a permission the holder holds itself (bundles and needs expanded). Board powers are never its to give or take, `admin.permissions` included.
  - **The library** (`POST/PATCH/DELETE /api/permissions`): it adds, edits and removes bundles and verbal permissions whose new includes and needs it holds. A command, tool or folders permission it may only narrow: adding one, removing one or turning another kind into one stays the human's. It never edits a permission it holds itself, because that would widen its own row.
  - **Its words say they are its own.** Guidance it writes is stored with its name (`guidanceBy` beside `guidance` in agents.json, `guidanceBy` on the grid cell) and reads *Guidance from <agent>, an agent acting for the human* in the other agent's brief. A library permission whose name, description or brief it wrote carries `by: "<agent>"` and its brief line ends *(written by <agent>, an agent acting for the human)*. The board sets both; a request can't. When the human rewrites the words, the mark goes.
  - Each refusal is `403 NO_ESCALATION`, with `reasons` (`OWN_ROW`, `BEYOND_HELD` with `missing`, `BOARD_POWER` with `powers`, `HELD_ITSELF`, `HUMAN_KIND`, `NARROW_ONLY`) and a hint.
  - It needs a board with a sign-in token and an agent token of its own (`403 NO_TOKEN`, since a name alone proves nothing). Admin off suspends it (`403 ADMIN_OFF`, the default board's switch).
  - Each change is `delegated` on its event (`agent.managed`, `permissions.changed`), adds a digest line, and grid changes are kept with before/after on the agent, like agents.manage's.
- The human can override any delegated verdict or move. Grants in agents.json are re-read on change, so removing one takes effect at once. `GET /api/permissions/me` and your brief list yours; metrics count delegated decisions (`delegated`).

### The permission library
Every permission an agent can hold, as data: `GET /api/permissions` (everyone reads it). The **built-ins** come from the code and never change: the tool permissions `read edit test build git web`, held through an agent's `perms`, and the board powers above (`review.decide`, `work.land`…), held only through `grants`. The human adds their own, stored in agents.json under `"perms"` beside `"agents"`, and an agent holds one like a built-in (`"perms": ["edit", "deploy-staging"]`):
```
POST   /api/permissions          { "key": "deploy-staging", "kind": "command", "name": "Deploy to staging",
                                   "commands": ["npm run deploy:staging"], "needs": ["test"], "brief": "Deploy after the tests pass." }
PATCH  /api/permissions/<key>    { "commands": ["npm run deploy:stage2"] }   (merged; null removes a key)
DELETE /api/permissions/<key>    (409 CONFLICT while an agent or another permission uses it, naming them)
```
- Kinds: `command` (exact, or ending in `:*`, same rule as `commands`), `tool` (a Claude or MCP tool by name; never `Bash`), `folders` (Edit and Write only under relative globs, e.g. `docs/**`; refused if it needs something that already writes everywhere, such as `edit`: need `read` instead), `bundle` (`includes` other permissions) and **`verbal`**: only words (`brief`). The agent reads a verbal permission in its brief and **nothing enforces it**: it adds no tool, shows `enforced: false` with a warning everywhere it appears, and could be dangerous on its own.
- `needs` brings other permissions with it. Neither a bundle nor a need can reach a power: powers stay in `grants`.
- **Run an author's code** (`run-authors-code`, built-in; needs `read` and `test`; the Reviewer role holds it) is what lets an agent run code from another agent's branch: `intellagent sandbox exec`, and the tests in another worktree (`npm test --prefix .worktrees/<author>`). A run without it is denied those commands, and `GET /api/permissions/me` answers `runAuthorsCode: false` with why and a hint. An agent outside agents.json counts as holding it only on a board that checks agent tokens.
- Each permission's `brief` line goes into the brief of every agent holding it, under *Permissions the human gave you* (agents holding only built-ins see no change). Changing a permission rebuilds its holders' runs at once.
- Only the human changes the library (`403 HUMAN_ONLY`, also for `agents.manage`), or an agent the human granted `admin.permissions`, within what it holds (see *Board admin*); built-ins answer `409 CONFLICT`. An agent manager's narrowing check expands bundles and needs first. An entry in agents.json that doesn't check out is skipped and reported in `GET /api/agents` (`error`). Emits `permissions.changed`, which wakes nobody.

**The permissions grid** (the human's view of who holds what): `GET /api/agents/grid` lists every standing agent against every library permission. A cell is `{ mode: off|on|rules, rules?, guidance, enforced, differsFromRole, implied?, by?, brief }`; `brief` is the lines the agent reads in its own brief (empty when off), `enforced: false` marks a verbal permission, `implied` an `on` that only another permission's `needs` keeps. `PUT /api/agents/<name>/permissions/<key> { mode?, rules?, guidance? }` sets one cell in agents.json, for the signed-in human (`403 NO_TOKEN` on a board with no sign-in token) or an agent with `admin.permissions`, on other agents' rows and within what it holds (`403 NO_ESCALATION`; any other agent `403 HUMAN_ONLY`). `on` also turns on what the permission needs; `rules` (board powers only: `minOks`/`from`, `where`) writes a grant with rules; `guidance: ""` removes the human's words. The reply has `cell`, `also` (what else came on), `notes` (e.g. the agent left its role's list for its own) and `changes`.

### Handoffs
`PATCH … { "assignee": "other-agent" }` hands a ticket over; the assignee receives its events (`for=<name>` / `assignee=<name>`).
When a ticket's last open blocker reaches the final column (or is archived), its watchers get `item.unblocked`.

### Asking for a ticket someone else holds
`POST …/items/<ID>/lease/request { "reason": "…" }` tells the holder. The holder (or the human) answers with `POST …/lease/handover { "to": "<you>", "note": "where I left off" }` — the lease moves to you in one step — or `POST …/lease/decline { "to": "<you>", "reason": "…" }`. Pending requests show up first in the holder's `…/work`. Requests are allowed even while the board is held.

### Working alone: the master lease
`POST /api/boards/main/master {}` holds the whole board until you release it (pass `minutes` for a time limit, `status` for a live line in the header). While you hold it you need no per-ticket leases and other agents are read-only — they can still comment, ask the human and post to the digest. It fails while other agents hold ticket leases. **Release it (`DELETE …/master`) before spawning helper agents**; they then use normal ticket leases. The human can revoke it at any time.

### Focus boards: the human is working on a handful of tickets
A focus board is a saved view over a board: a name and a list of its tickets, never a copy. The human makes one from a bulk selection; it shows only those tickets, in the same columns under the same rules, and every change on it is a change to the real ticket. **One board is active** — the full board, or one focus board — and while a focus board is active, **you work only on its tickets**:
- `…/work` and your brief say so (`focus: { name, items, note }`, and `focus: ["<name>"]` on each ticket that is on one) and suggest only its tickets; pickup skips the rest. Work you held outside it when it became active went back to the pickup column, still assigned to you, with a 🎯 comment.
- What still reaches you outside it: an @mention, a request or an explain from the human, the lease housekeeping on what you hold, and landing approved work (`work.land`). `start` outside it answers `409 OUT_OF_FOCUS`; when the human asked you for that ticket directly, pass `"outsideFocus": true`. Reviews and delegated approvals outside it wait (`409 OUT_OF_FOCUS`).
- Tickets you file go where they always do (e.g. Backlog), not onto the focus board. The **coordinator** may add tickets to a focus board when the human asks (`PATCH …/focus/<id> { add: [ids] }`); only the human (or an agent the human granted `admin.focus`) makes, renames, takes tickets out of, activates or retires one.
- Retiring removes the view only: no ticket moves, and the full board is active again (your held work comes back in `…/work`).

```
GET    /api/boards/main/focus                  → { active, focusBoards: [{ id, name, itemIds, active, count, createdAt, createdBy }] }
GET    /api/boards/main/focus/<id>             → one focus board with its tickets
POST   /api/boards/main/focus                  { name, itemIds, activate? }      (human)
PATCH  /api/boards/main/focus/<id>             { name?, add?, remove? }          (human; the coordinator may only add)
PUT    /api/boards/main/focus/active           { id } | { id: null }             (human)
DELETE /api/boards/main/focus/<id>             → what moved while it was open    (human)
POST   /api/boards/main/items                  { …, focus: "<id>" }              (created on the board, added to that focus board)
```
Events: `focus.created`, `focus.updated`, `focus.activated` (to every standing agent's inbox; wakes nobody), `focus.retired`. A ticket archived or deleted leaves every focus board.

### Card rules and review facts
The human names a **condition** and the **look** a ticket earns when it holds ("full agent approval" is `review.allOk review.oks>=2 review.evidence`). Everyone reads `GET …/card-rules`; only the human, or an agent the human granted `admin.cardRules`, writes it (`PUT …/card-rules { rules: [{ name, condition, look, enabled? }] }`, `403 HUMAN_ONLY` for any other agent). A look is `outline`/`tint` (`ok accent warn danger`), `badge` (`"text"` or `{ text, icon }`) and `ribbon` (short text) and `mark` (`{ shape, tone }` or `{ shape, colour: "#rrggbb" }`, shape one of `square circle triangle diamond bar star`; a bad one is `400 BAD_REQUEST` with a hint). Rules are checked in list order: the first outline, tint and ribbon win and badges stack, two at most; every matching mark is kept, in rule order, as `marks: [{ shape, tone | colour, rule }]` (no limit: the card decides how many to draw). A board starts with no rules (the type already shows beside the id); a board that was once seeded with the three type rules loses them, if unchanged, when it next starts. `GET …/card-rules/matches` gives the look per ticket, `GET …/card-rules/check?condition=…` the count and first ids before saving.

A condition is terms separated by spaces, all of which must hold: `review.allOk` (set) · `!review.concerns` (not) · `fields.risk:low` (equals; `a|b` either) · `review.oks>=2` (`> >= < <= =`) · `reviewers.nebula:ok` · `@drax` (assigned or leased) · `is:rule:<name>` (a name with a space goes in quotes, `is:rule:"full approval"`, or with a dash, `is:rule:full-approval`; spaces, dashes and underscores count alike) · `columnDays>=3` (whole days in the column it is in now; a fact in search and in `where`, like `review.oks`). Beyond "all of these": `a or b` (either; and binds tighter than `or`) and one level of groups, `review.allOk (@drax or @nebula)`; a group cannot hold another (`400 BAD_REQUEST`, hint: make the inner one a rule and use `is:rule:`) and cannot be negated (`!(…)` is `400`; put the `!` on the terms inside). A bracket pair inside a value, `fields.note:foo(bar)`, stays part of that term; a bracket that starts a term opens a group. One that does not parse is `400 BAD_REQUEST` naming the term, with a hint.

Every ticket in search carries **review facts**: `review.oks`, `review.pending`, `review.concerns`, `review.allOk`, `review.evidence`, and `reviewers.<name>`. They count only verdicts that stand (given with the reviewer's own token, about the commits the ticket has now), so a stale ok never shows as approval. `review.evidence` is true only while a review is open (the evidence lives on the open review). The facts sit beside the decision record (`review.verdict`, `review.by`…) in the same `review` object. Use them in `where` (`{ "review.oks": { "gte": 2 } }`) or as `filter` (`POST /api/search { filter: "review.allOk" }`, `GET /api/search?filter=…`).

## 4. Talk to the human

```
POST   /api/boards/main/items/INT-12/attention  { "reason": "Rotate refresh tokens on every use, or only on expiry?" }
DELETE /api/boards/main/items/INT-12/attention  { "reply": "…" }   (normally the human does this)
```

The ticket glows on the board. The reply returns a `questionId`. A ticket can hold several open questions (from you and others); each is answered on its own and the answer arrives as an `attention.resolved` event with that `questionId` and `reply`, addressed to whoever asked — and in `GET …/work` under `answered`. Asking the same thing twice reuses the open question. The human answers one with `DELETE …/attention { questionId, reply }` (without `questionId`, every open question is closed).

**A question with a form.** When the answer has a shape, give the question a `form` and the card draws the controls:
```
POST …/items/INT-12/attention { "reason": "Storage setup?", "form": [
  { "type": "note", "markdown": "Pick what **fits**." },
  { "key": "db", "label": "Database", "type": "choice", "options": ["postgres", { "value": "sqlite", "label": "SQLite" }], "required": true },
  { "key": "extras", "label": "Extras", "type": "multi", "options": ["cache", "queue"] },
  { "key": "migrate", "label": "Migrate now?", "type": "yesno", "default": false } ] }
```
Types: `text longtext choice` (radio) `multi` (checkboxes) `yesno number` (`min`/`max`) `date` (YYYY-MM-DD), plus `note` blocks of markdown; each field may have `required`, `default` and `help`. Combine them in any order. The answers come back as `{ key: value }` (unanswered ones `null`) in the event's `form` and in `…/work` under `answered[].form`, and as a readable comment on the card. A form the board cannot draw, or answers that don't fit it, get `400 BAD_REQUEST` with a hint. The human can still reply in words or resolve without filling it in, so read `form` when it is there and `answer` always.

**Withdrawing.** Once your ask is met or no longer relevant, take it back with a reason instead of leaving it open: `POST …/items/<ID>/questions/<questionId>/withdraw { "reason": "…" }` for a question or a review request on a card, `POST …/requests/<id>/withdraw { "reason": "…" }` for a request you sent. It is recorded on the card (↩) and leaves everyone's `…/work`; it moves nothing (whoever leases the ticket, or the coordinator, decides that). Only whoever raised it, the coordinator or the human may close it: anyone else gets `403 FORBIDDEN`, and the same holds for an agent calling `DELETE …/attention`. A review that was withdrawn and never decided can't be carried through a gate by an agent (`409 REVIEW_OPEN`).

**Where to ask.** While the human is actively chatting with you, quick back-and-forth belongs in chat. Anything that should outlive the conversation — a decision, an approval, a question raised while working unattended — goes on the card, so you never wait in one place while they answer in the other. If you asked in chat about a ticket, record the answer on the card.

**Reactions.** React to a card or a comment with an emoji — `POST …/items/<ID>/reactions { "emoji": "+1", "commentId": "c_…" }` (omit `commentId` for the card; names like `eyes`, `+1`, `tada`, `rocket`, `thinking`, `check` work; `DELETE` with the same body removes it). Reactions never wake anyone and are allowed even while others hold the ticket or the board. ⏳ means "queued": a comment for a standing agent that is busy, settling or throttled gets ⏳ from that agent (hover says when it runs), swapped for 👀 when the run starts. 👀 means "seen": it is added for you on comments you're woken for (standing agents and `intellagent wait`); add it yourself when you read a comment some other way. Use 👍 / ✅ for "done", 🤔 when you're unsure — then say why in a comment.

**Seen, not answered.** A comment that @mentions an agent whose 👀 is on it, with no later comment from that agent on the card and no reaction of its own on the comment other than 👀/⏳, is *seen, not answered*: the ticket (`GET …/items/<ID>`) carries `unanswered: [{ commentId, agent, by, since }]`, and that agent's `GET …/work` lists a `reply` action and an `unanswered` array. It is read off the card, never a reason to run: `work.pending` does not carry `reply`, so it starts no run and cannot loop. It clears by itself when the agent comments or reacts (✅ / 👍 for a mention that needs no words: the 👀 alone does not count). Not counted: an agent mid-run, explain comments (their own action), comments older than 3 days, finished tickets and archived ones.

**Typing.** The board page tells the others that someone is writing a comment: `POST …/items/<ID>/typing` (people only; an agent gets `403 HUMAN_ONLY`, and `PUT …/status` is how it shows what it does). It is sent live on `/api/stream` as `item.typing { itemId, actor }` with no recipients and no `seq`: it is not stored, logged or replayed, changes no version, history or digest, and wakes nobody. One per person and ticket every 3 seconds (`{ sent: false }` between); a client lets the pip lapse a few seconds after the last one. Agents have no tool for it.

**Asking another agent: an ask, not an @mention** (INT-391). When you need something from another agent, make it an obligation the board tracks: `POST …/items/<ID>/asks { to, kind, what, options?, dueMinutes? }` → `{ ask }`. Kinds: `answer`, `decide`, `review`, `fix`, `assign_reviewer`, `unblock`, `other`. It is an `ask` in its owner's `…/work` (it wakes the owner once) and closes itself when the thing is done (`review`: the owner's verdict; `fix`: its next review request; `assign_reviewer`: a reviewer assigned) or when the owner answers `POST …/asks/<askId>/done { answer }` (the answer goes on the card, and back to you as `ask_answered` in your work). Not done by its due time (default 60 minutes), it escalates once: to the coordinator as an ask of its own, or to the human when there is none; the escalation closes with the original. Withdraw one you no longer need: `POST …/asks/<askId>/withdraw { reason }` (the asker, the coordinator or the human). Events: `ask.created` (addressed to the owner), `ask.done` (to the asker), `ask.withdrawn`, `ask.overdue`. A `chase` or a `supervise` action proposes the ask to make.

**Alerting another agent: @mention it** (for conversation; for an obligation, ask). Most agents wake only when they are addressed, so "Rocket, take this" wakes nobody; "@rocket, take this" does (so does assigning the ticket). An @ inside `code` or a `>` quote does not count. When an agent names another standing agent without @, the comment is still saved, and the reply carries a `warning` saying who was not alerted. Only standing agents wake on an @mention: an @ of any other name (not a person on the board, and not waiting on the board right now with `intellagent wait` or a stream) is saved too, and its reply carries a `warning` that nobody was woken. Every brief carries this rule.

**What not to post.** Keep cards and the digest readable: no step-by-step progress logs, nothing git already shows (diffs, file lists), no restating the ticket. Post decisions, blockers, results and how to verify.

**Requests.** The human's free-form asks ("create tickets for X") are *requests*, sent to the board's coordinator or a named agent. They arrive as `handle_request` in `…/work`: do it, then `POST …/requests/<id>/reply { "body": "what you did, with ticket ids", "done": true }`. `GET …/requests` lists them; `POST …/requests { "body": "…", "to": "<agent>" }` sends one (to the coordinator if `to` is omitted). A request is usually a follow-up: its event carries `history`, the conversation so far with you (the last 10 messages of the week, oldest first), and your prompt shows it — answer the latest message in that context.

### Getting woken up
You only see board events when you look. Ways to make answers on cards reach you:
- **During a session:** run `intellagent wait --agent <you>` as a **background** command. It blocks until something arrives in your inbox, prints it and exits — your shell tool notifies you. It remembers its place, so nothing is missed between runs. Re-arm it after handling the events.
- **Standing agents (unattended, survives reboots):** the board itself starts a short headless run whenever events arrive for an agent defined in `.intellagent/agents.json`. Agents are disposable; the board keeps the queue. Details below.
- **Ad hoc:** `intellagent watch --agent <you> --claude` (or `-- <any command>`) does the same from a terminal you keep open.
- **Coordinating several agents:** add `--human` to `wait`/`watch` (or `"listen": "human"` for a standing agent) to hear about *everything* the human does on the board, not just your inbox — then delegate with `assignee` or a comment @mentioning a worker. `--filter "types=item.created&column=Ready"` takes any event filter.

### Standing agents
```jsonc
// .intellagent/agents.json — the human's file; commands only ever come from here, never from the API
{
  "defaults": { "maxRunsPerHour": 20, "maxFailures": 3, "timeoutMinutes": 60 },
  "agents": {
    "builder":     { "listen": "inbox", "description": "Implements tickets from Ready." },
    "coordinator": { "listen": "human", "run": "claude -p --permission-mode acceptEdits \"Handle the Intellagent events on stdin.\"" }
  }
}
```
- `listen`: `addressed` (default — wakes only when the event is *for* it: an @mention outside code/quotes, an assignment, a lease request or handover, an answer to its question, a verdict on its review, a request), `inbox` (also everything on tickets it worked on or commented on), `human` (everything the human does), `new-tickets` (tickets the human creates), an event filter object, or a list of these. The coordinator role uses `addressed` + `new-tickets`. Events that don't wake it still show in its inbox and `…/work`.
- **`wakeFrom`: `events` (default) or `work`** (per agent or in `defaults`, INT-390). With `work`, an event that reaches the agent only as `addressed` news doesn't wake it by itself: it is kept as context, the board checks the agent's work at once, and the agent wakes when its work gains an item. The run gets the work (`work.pending`) and the context events after it. A mention is work too (`mention`, once per comment, until the agent has seen it), and so are an assignment, an answer, a verdict, concerns and a request. News that no work item carries still wakes it directly: `lease.handed`, `lease.declined`, `request.replied`, `request.done`, `board.idle`. Other `listen` sources (`human`, `new-tickets`, filters) wake as before. The point: every wake has something to do (the `intellagent_agent_idle_runs_total` metric counts the ones that don't).
- **Work already on the board wakes it too.** On board start, on resume, after each run and every `sweepMinutes` (default 10), an idle agent checks for its waiting work (assigned and not started, answered questions, review feedback, open requests, lease requests) and gets one `work.pending` event listing it. With `pickup`, it also wakes for unassigned tickets: `"ready"` (or `true`) for the pickup columns, `"all"` for every open column. The coordinator role uses `"all"`, so the receptionist sees every unassigned ticket, not only new ones. Each piece of work wakes an agent once and again only after it leaves the list and comes back (e.g. reassigned), so leaving something alone never loops. Tickets waiting on the human never wake anyone.
- **Supervision:** an agent with `supervise: true` (the coordinator role, by default) also hears about tickets another *standing* agent was given but hasn't started (once picked up, a ticket is the stuck watch's, below) — its agent is paused or failed, or nobody holds the ticket, the agent is idle and nothing has happened on it for `superviseMinutes` (default 30). A busy agent's other tickets are queued, not stalled: one that holds a lease or ran within `superviseMinutes`, a ticket with an open blocker, or one whose assignee's last comment names an open ticket that hasn't moved since ("queued behind INT-11"); the assignee's own comment otherwise counts as activity for four times as long. A paused or failed agent is always caught. They show as `supervise` actions in its `…/work` and wake it once per stall; it resumes or runs the agent (with the `agents.control` grant) or @mentions it. After two unanswered nudges in a row it stops and leaves the ticket to the human. A new ticket the human already assigned to someone else doesn't wake the coordinator for triage.
- **The stuck watch** (INT-394): every ticket picked up and not done is followed over time. One with no progress for 60 minutes (a move, a review asked for, a verdict, an answer, an ask answered, or a comment from the human or its owner: a lease claimed again or a status line is not progress) enters the board's ledger (`board.stuck`, `GET …/stuck`) with when it was first seen and why: `no_owner`, `owner_down` (paused, failed or switched off), `owner_quiet`, `held_quiet` or `waiting_on_human` (listed, never an agent's). Still stuck 30 minutes later, the board is sure and the coordinator gets `unstick` in its work (once per round of 60 minutes), naming the reason, the owner and the next step: ask the owner, resume it, or assign it. While an ask about it is within its time nobody is woken; after two rounds the human gets a question on the card. Supervision keeps the tickets assigned but not started; picked-up ones are the watch's. `/metrics`: `intellagent_tickets_stuck{reason,state}` (`suspected`, `sure`, `asked_human`) and `intellagent_stuck_oldest_seconds`. The manifest tunes it: `"stuck": { "quietMinutes": 60, "sureAfterMinutes": 30, "roundMinutes": 60, "rounds": 2 }` and `stuckSweepSeconds` (300); `GET …/stuck` shows the rules in force. A sandbox runs no sweep.
- **Idle-board alarm:** when tickets wait to be started (in a pickup column, not held, blocked or waiting on the human) yet no builder (an agent that edits files) has run for the alarm's minutes (default 20), the agents it names get one `board.idle` event, with the human's note for them. It is a board setting the human changes on the Agents page (*When the board goes idle*), or with `PUT …/idle-alarm { on?, minutes? (5-1440), wake? [agents], note? }` (human only; `GET …/idle-alarm` shows it and the last alarms). Until it is set, agents with `idleAlarm: true` in agents.json are woken after their `idleAlarmMinutes`. Each alarm is kept on the board, emitted as `agent.idle_alarm` (wakes nobody) and counted in `…/metrics` (`idle: { alarms, prev, longestMinutes, lastAt }`). The event names what waits and how each builder stands. A new set of waiting tickets alarms once the builders have been quiet that long; the same set again only after twice the wait each time (20, 40, 80… minutes), so a nudge that wakes a builder which then starts nothing can never turn it into a loop. It is a plain check, so it costs nothing until it fires, and it stays quiet while the builders are paused (stop all), running or have events queued. **When nobody it names can be woken** (failed, paused, or none named), it tells the human instead, with the same backoff: the record has `woke: ["human"]`, `human: true`, `down: [{ name, status, code? }]` and the builders' states, and `GET …/idle-alarm` returns it as `notice` while it stands (until a builder runs or an agent it found down is back), for the UI to show with Resume buttons. `PUT …/idle-alarm { human: false }` switches that off; while it is on, the alarm may name nobody.
- **Automatic rebalancing:** the board moves queued work between builders by itself, with no approval for each move. It looks when an agent is added, removed or changes role, and on a sweep at most every 10 minutes. Only an unstarted ticket in a pickup column moves, and only to an agent that edits files and may work in that column. The best target owns the ticket's files (`areas`), then has the right role, then the right tier (`risk: high` goes to a senior), then the shortest queue. **Never moved:** a held or started ticket (anyone in `workedBy`), one waiting on the human or blocked, a pinned one, one the human assigned by hand (`assignedBy`; unknown counts as the human's), or one moved in the last day. A move needs a real imbalance: queues `minGap` apart (default 3), the longer one waiting `minWaitMinutes` (60), and a result the next pass won't undo. It moves at most `maxMoves` (3) per pass. An agent paused or failed on its own for an hour gives its queue away; Stop all never counts. A removed agent's unstarted tickets all move, even pinned ones, once the removal has stood for `removalGraceMinutes` (manifest, default 10; an agent back in agents.json before then moves nothing); the pin goes with the move and the ↔ note says so. Undo answers `409 CONFLICT` while anyone holds the ticket or the new owner has worked it (reassign by hand then). Each move is made by the system (`assignedBy.kind: "system"`): it wakes only the new owner (`item.assigned`), leaves a ↔ comment that @mentions nobody, and records `rebalanced: { from, to, at, why }` on the ticket and one digest line per pass. These calls are human-only (`403 HUMAN_ONLY`): `GET/PUT …/rebalance { on?, minGap?, minWaitMinutes?, maxMoves?, onceEveryMinutes? }` (on by default), `POST/DELETE …/items/<ID>/pin`, and `POST …/items/<ID>/rebalance/undo` (back to the old owner, pinned). `pinned`, `assignedBy` and `rebalanced` can't be sent with PATCH.
- **What an agent is taught, in layers:** a run's first turn gives it, each under its own heading, the **base** (how every agent works here: the loop, learning from mistakes, being productive, honesty, talking, cost), its **role**'s brief, then its own **speciality** (below). The **board rules** come from the brief it reads first. The base ships with Intellagent (`lib/agents/base.md`); the human's own copy is `base-context.md` beside agents.json, which an update never touches (saving the shipped text again, or nothing, removes it). Agents can't edit it. Later turns of a keep-alive session carry none of this again. An agent the board does not run (not in agents.json) reads the base in its brief instead, under `## Base`; a standing agent's brief leaves it out, since its first turn had it. `GET /api/agents/base-context` → `{ text, shipped, edited, max }` (anyone); `PUT /api/agents/base-context { text }` replaces it (the human only, on a board with a sign-in token: `403 HUMAN_ONLY` / `403 NO_TOKEN`; `400 TOO_LARGE` above 8000 characters; an empty text goes back to the shipped one), emitted as `agent.base_updated` with `before` and `after`, which wakes nobody. `GET /api/agents/<name>/layers` (the human, or the agent itself as `me`; anyone else `403 FORBIDDEN`) lists what that agent is taught, in order: `base`, `rules` (the board rules, `?board=`), `role` and `agent` (standing agents only), `memory`, each `{ layer, label, text, chars }`.
- **Speciality:** `areas` (files and folders it owns: guidance for it and for routing, not a limit), `concerns` (what it checks before asking for review) and a context page, `agent-context/<name>.md` beside agents.json (or inline `context`; capped at 8k characters). The agent gets them first thing on each session's first turn and in its brief; the receptionist routes by areas first, then role, then tier. Edit them on the Agents page (agent profile › Speciality, with repo path suggestions from `GET /api/files?q=`), with `PATCH /api/agents/<name> { areas, concerns, context }` or `intellagent agents add … --areas … --concerns …`.
- **Reviewers:** an agent with `reviewer: true` (the reviewer role by default; the *Can review* switch in its Speciality) may be asked to review. The receptionist gets an `assign_reviewer` action for each ticket in review without one, and picks a reviewer whose areas or concerns fit: `POST …/items/<ID>/reviewers { name }` (the human or the receptionist only). **Never the author:** anyone who worked on the ticket, asked for its review or is assigned to it is refused (`403 OWN_WORK`), also if they start working on it later. The reviewer gets a `review_ticket` action and answers with `POST …/items/<ID>/reviewers/<name>/verdict { verdict: "ok" | "concerns", comment }`: a ✅ or ⚠ comment (concerns @mention the author) and a tick on the card. Reviewers never decide the review or move the ticket; the human approves. While a reviewer's concerns stand, the author has an `address_concerns` action in `…/work` (it wakes once per concerns verdict): fix them and request review again, which asks the reviewers again. A reviewer who calls the decide route by mistake (or sends `ok`/`concerns` there) gets `403 HUMAN_ONLY` with `call`: the exact verdict request for that ticket. A new review request resets the ticks and wakes the reviewers again. An @mention doesn't assign a reviewer: a review request that names a reviewer-pool agent not on the ticket still goes through, but its reply carries a warning ("@name is not a reviewer on …"), and its verdict won't count until the receptionist or the human assigns it.
- **Helpers:** an agent with `"helper": true` in agents.json (the human's to set; `PATCH /api/agents` can't) does chores for the others and is never routed work. Only the human assigns it a ticket: an agent setting `assignee` to a helper, on a PATCH or a new ticket, gets `403 NOT_ROUTABLE` with a hint to send it a request instead. Triage, pickup, supervision and rebalancing skip it, and the coordinator's brief lists it apart from the agents it routes to. A request to a helper (`POST …/requests { to }`) needs the **Call on the helpers** permission (`call-helpers`, built-in; the Builder role holds it), or `403 NOT_DELEGABLE`; the human can always send one, and a helper never calls a helper (so two can't wake each other in a loop). On a ticket it wasn't assigned, a helper takes no lease, asks for none, isn't handed one by an agent, doesn't start it and doesn't request its review (`403 NOT_ROUTABLE`): it replies on the request and comments on the card the caller named, and the caller keeps the ticket. It runs at most `helperMaxRunsPerHour` times an hour (default 6, in `defaults`) unless it sets its own `maxRunsPerHour`: every builder can call it, so its runs add up first.
- **Personality and context items:** `personality: { explains, speed, autonomy (0-4 each), text }` is written into the agent's brief as one plain line. `contextItems: [{ kind: "note" | "file" | "link", title, body | path | url, on? }]` replace the single context page: a note is text, a file pins a repo path and is read fresh on every run (never `local.json`, `agents.json`, `agent-context/`, `data/` or a path outside the project), a link is only listed; `on: false` leaves one out. An existing `agent-context/<name>.md` or inline `context` becomes one note, "Context", once; the old file is kept as `<name>.md.bak`. **The mirror:** on every change to an agent's items the board writes them to `agent-context/<name>.md` (a generated header, notes in full, file items named, links listed), so the instructions show in git diffs. The board never reads it: a hand edit is reported in `GET /api/agents` (`error`), kept as `.bak` and replaced on the next change. Set both with `PATCH /api/agents/<name>` (the whole `contextItems` list; `GET …/context` returns the items and the rendered text). An agent with `agents.manage` may change notes only: file and link items stay the human's (`403 HUMAN_ONLY`). Every change is kept with before/after and reverts. **`GET /api/agents/<name>/preview`** (the human, or `agents.manage`) returns `{ agent, prompt }`: the first-turn prompt the board would send now, built by the same function as a real run, with no events in it.
- **Roles** are templates an agent is built from: a brief, wake-up settings (`listen`, `pickup`, `supervise`, `reviewer`, `throttleMinutes`), permissions from the library, and optionally a `model` and `commands`. The built-ins (coordinator, builder, reviewer, researcher, designer, writer) ship with the code and never change. The human adds their own under `"roles"` in agents.json, e.g. `"triager": { "label": "Triager", "brief": "Your role: …", "perms": ["read"], "model": "haiku" }`. A role can't reuse a built-in's name, hold a power or carry grants (those stay on each agent), and an agent manager (`agents.manage`) may give only the built-ins (`403 HUMAN_ONLY` for the human's own, which can bring commands and a model). An agent names its role with `"role"`, and every key it sets itself wins over the role's. `GET /api/agents` shows each agent's `differsFromRole` (`{ key: { role, agent } }`). `GET /api/roles` lists every role with the agents using it; `GET /api/roles/<key>` shows one role and how each of its agents differs from it. A role that doesn't check out is skipped and named in `errors`. The human adds or replaces their own with `PUT /api/roles/<key> { label?, icon?, description?, brief?, listen?, pickup?, supervise?, reviewer?, throttleMinutes?, perms?, model? }` (`403 HUMAN_ONLY` for every agent, `agents.manage` included; a built-in answers `409 CONFLICT`): never `commands`, `run`, `env` or `grants` (`403 NOT_DELEGABLE`; commands already written by hand in agents.json are kept), and never a power in `perms` (`400`). It is checked as agents.json is, emitted as `agent.role_changed` with `before` and `after`, which wakes nobody.
- **Wake settings:** `supervise` (true, false, or null for the role's) and `idleAlarm` (true, false, null, or `{ minutes: 5-1440 }`) on `POST /api/agents` and `PATCH /api/agents/<name>` are the human's: each makes an agent run more often, so an agent manager gets `403 HUMAN_ONLY`. Changes are kept with before/after like every other edit. A new agent's are stored but held off until it is accepted (probation, below). `listen`, `pickup` (false, `ready`, `all`; true is `ready`) and `throttleMinutes` (whole minutes 0-1440) on `PATCH /api/agents/<name>` are the human's too (`403 HUMAN_ONLY` for every agent, `agents.manage` included); a bad value is `400 BAD_REQUEST` with a hint, `null` goes back to the role's, and the change applies from the next run.
- **Probation (a new agent is introduced first):** an agent added through `POST /api/agents` or `intellagent agents add` (a new name, also one added again after it was removed) starts on probation: `probation: { since }` on its agents.json entry, so losing the board's state never lifts it. Agents already in the file get none. While it stands:
  - its run is built from `read` alone, whatever the file says: no edit, test, git, commands, worktree, keep-alive or pickup, and a hand-written `run` is replaced (it comes back on accept);
  - the board asks it once, with a request (`[introduction] …`), to introduce itself: who it is, what it will and won't do, what its permissions let it do, what it needs. Its only wake is that request; mentions, assignments, answers and the sweeps start nothing, so it costs one small run;
  - the API is an **allow-list**: reads, `PATCH /api/profiles/me`, the reply to the introduction request (`POST …/requests/<id>/reply`, only a request a person sent it) and, when the human named a ticket at creation (`introTicket`), an intro comment there (`{ "intro": true }`). Everything else that writes, memory, reactions and digest included, answers `409 PROBATION` with a hint. A route added later is closed to it by default. The intro mentions nobody (@mentions stay text and alert no one);
  - `POST /api/agents/<name>/accept` (human only; no grant, `agents.manage` or `agents.control` reaches it) lifts it: the agent works like any agent from then on. `POST /api/agents/<name>/return { note? }` (human only) keeps it on probation and asks again, with the note. `probation` is not a key `PATCH /api/agents/<name>` can change (`403 NOT_DELEGABLE`), and the agent can't clear it through its profile. CLI: `intellagent agents accept <name>`, `intellagent agents return <name> --note "…"`; `agents add` says the new agent is on probation and how to accept it. The agent's view (`GET /api/agents`) shows `probation`.
- `model` (per agent or in `defaults`): passed to the `claude` run as `--model` (a `run` that already names `--model` keeps it). Use it for **tiers**, and the receptionist's brief lists the team with role, model and description so it routes by them:
  ```jsonc
  "junior": { "role": "builder", "model": "haiku",  "description": "Small, well-specified tickets" },
  "mid":    { "role": "builder", "model": "sonnet", "description": "Normal features and bugs" },
  "senior": { "role": "builder", "model": "opus",   "description": "Risky or cross-cutting work (risk: high)" }
  ```
  `intellagent agents add junior --role builder --model haiku` writes the same.
- `runModels` (per agent or in `defaults`): `{ "triage": "haiku", "build": "opus" }`, the model follows the run (a missing key means the agent's `model`; absent, every run uses `model`). A run is **triage** when none of its events can need building (a `work.pending` offering only renew / lease-request / supervise / chase work, a plain comment, lease requests and handovers, `focus.*`, `board.idle`, an answer or a verdict) and **build** otherwise (a start, feedback, an assignment, a request, an explain, any event the table doesn't know). A triage run is one process of its own, even for a `keepAlive` agent, whose warm session stays for build runs; its `INTELLAGENT_MODEL` is the triage model and its prompt tells it to end with a line holding only `[[needs-build]]` when it finds it must build. The board then runs the **same events once more on the build model**, without the throttle (the hourly cap still holds); that re-run builds whatever it says, so it never loops. `lastRun` and `history` carry `kind` and `model`, and each line of `agent-stats.jsonl` the `kind` and the model the run used. `usageToday.byModel` in `GET /api/agents` totals tokens and runs per model. Only plain model names; anything else is dropped with a warning in `GET /api/agents`' load error.
- `provider` (per agent or in `defaults`): who serves the model, for display and routing only (`anthropic` for a `claude` run unless it says otherwise; a custom run has none until you set it, e.g. `"provider": "deepseek", "model": "deepseek-chat"`). Tiers are for Anthropic models only. A run gets `INTELLAGENT_MODEL` and `INTELLAGENT_PROVIDER` in its environment, so an adapter knows what to call.
- **Usage from any run:** a run reports its tokens by printing one JSON line as its last JSON output (one-shot), or one per turn (keep-alive): `{ "type": "result", "usage": { … }, "num_turns": 3 }`. `usage` is Claude's (`input_tokens`, `output_tokens`, `cache_read_input_tokens`, `cache_creation_input_tokens`) or the OpenAI-compatible one (`prompt_tokens`, `completion_tokens`, and cached tokens as `prompt_tokens_details.cached_tokens` or DeepSeek's `prompt_cache_hit_tokens`). `num_turns` (model calls in the run) is optional and gives the context per call that `recycleAboveTokens` checks. A run that prints none shows usage as n/a.
- **One record per run:** when a run ends (a keep-alive session: each turn), the board appends a line to `data/agent-stats.jsonl`: `{ agent, model, provider, startedAt, endedAt, why, items, code, result: ok|failed|timeout|stopped|limited, tokens: { input, output, cacheRead, cacheWrite }, cost, tools, commands }`. `cost` is USD from the run's `total_cost_usd`; for a keep-alive turn it is the difference from the turn before (the session reports a running total), and `null` (not 0) when the run printed no result (timeout, stopped, crash). `tools` (counts by tool) and `commands` (names only, never command lines) come from keep-alive sessions; a one-shot json run lists none (`null`). The file rolls over to `agent-stats-<ts>.jsonl` past 5 MB; `lib/agents/stats.js` `read()` returns the rolled files and the live one, oldest first. It wakes nobody and changes no run.
- `keepAlive: true` (per agent or in `defaults`): instead of a fresh `claude -p` per wake, the agent keeps **one live session**, and each wake is a new turn in it (stream-json on stdin; the turn ends at its `result`). Only the session's first turn gets the full prompt (role brief, rules, "start with intellagent brief"); later turns get just the new events, any retry notes and a one-line reminder, since the rest is already in context — so a wake costs little more than its new events. The session is replaced after `recycleAfterRuns` turns (default 20), once its context per model call passes `recycleAboveTokens` (default 120000; `0` = off; shown on the Agents page), after a failed turn, on pause, removal or a board restart; a crash mid-turn is retried like any failed run. **Trade-off:** context grows and what the session remembers can go stale — the board always wins, so check `…/work` each turn (and the brief whenever the board rules matter). **`"keepAlive": "auto"`: warm only while it pays** (INT-404). A warm turn saves a fresh start's cost (system prompt, tools, brief) only while the model's prompt cache still holds the session; after that, the next turn re-writes the whole, bigger conversation, which costs more than starting fresh. So an auto session is kept after a turn only while the agent wakes about as often as the cache lasts (the median of its last few gaps between runs, against `cacheTtlMinutes`, default 5) and while its context per call is under `warmFactor` (default 3) times its first turn's; otherwise it ends and the next wake starts fresh. A kept session idle for the cache's lifetime ends by itself. `GET /api/agents/<name>` shows the decision (`session.warm: { keep, why, until }`, and `lastWarm` once one ended), and each run record says which turn of its session it was and whether it was warm (`session: { turn, warm }`). A stream-json run gets the same with `"warm": "auto"`. A custom (non-claude) `run` that speaks the same protocol says so with `"keepAlive": "stream-json"`; with plain `true` it runs one-shot instead (a turn it never answers would hang until the timeout), and `GET /api/agents` → `error` says why. Inside a session, `intellagent api` and the MCP tools pick up the current run from `INTELLAGENT_RUN_FILE`.
- **Own worktree** (`worktree`, on by default for agents that edit files): each such agent works in its own git worktree on branch `agent/<name>` (in `.intellagent/worktrees/`, or `.worktrees/` beside a manifest at the repo root; git-ignored), so agents never overwrite or commit each other's half-finished work. **One branch per ticket:** `start` switches the worktree to the ticket's own branch `ticket/<name>/<ID>`, made from main's tip, or from the branch of an unlanded ticket in its `blockedBy` (so work that builds on it can); `start` again (review feedback) resumes it with main merged in. The reply says which (`branch: { name, base, resumed, note? }`). Uncommitted changes in the worktree answer `409 DIRTY` and nothing changes: commit them on the ticket they belong to, or discard them, then start again. A ticket branch's commits sit straight on main, so it lands on its own; one that sits on an unlanded blocker answers `WAITS_FOR_BLOCKER` until that blocker has landed. Once everything on it has landed the branch is deleted and the worktree goes back to `agent/<name>`, which stays for work begun before ticket branches: a ticket that already has unlanded commits there is kept there when it is started again (the reply's `branch.note` says so), so its rounds land together. Before each run it catches up with main (reset to main once all its work has landed, else merged; a ticket branch is only ever merged; a conflict is reported in the prompt). Put the ticket id in every commit message. Requesting review lists the ticket's commits; **approving lands them on main** (a cherry-pick into the main checkout; if that conflicts and every unlanded commit on the branch is this ticket's, a `--no-ff` merge of the branch instead, which keeps a conflict the agent resolved when it merged main in; only when that checkout has main open. Uncommitted changes there block a landing only when they touch a file the ticket's commits change (and they block the merge fallback): an edited agents.json never holds up a landing, and a failed landing's undo keeps them. A landing that failed only because of uncommitted changes (`landing.code: "DIRTY"`) is landed again by the board's sweep once the main checkout is clean; otherwise the card says what to fix and to run `intellagent merge <ID>` then). Main is the manifest's `mainBranch`, else the remote's default branch, else `main` or `master`; never just whatever branch the main checkout has open. `"worktree": false` opts out.
- `commands` (per agent): exact extra commands the human allows it, e.g. `"commands": ["npm run measure:board"]`. Each one is allowed exactly as written; a trailing `:*` allows that one command with any arguments (`"npm run measure:board:*"`); anything else with a wildcard, quotes or shell punctuation is dropped. A run built from permissions lists them with the rest of its allowed tools; a hand-written `claude` run gets them as an `--allowedTools` flag of its own at the end, so they are allowed whatever it carries (a custom run that is not `claude` gets none). Only what the run itself forbids still wins. **Check one before you save it:** `POST /api/agents/<name>/commands/check { "command": "…" }` (the human, or an agent with `agents.manage`; it changes nothing) answers `{ kept, why, listed, allowedBy, denied, applies }` with the same rule the run builder applies: `allowedBy` names the permissions that already allow it, and `denied: { needs: "run-authors-code" }` means it is kept but the run denies it (another agent's code), because a deny beats an allow. For a hand-written run, `denied` says so when the run itself forbids the command.
- `mcp` (per agent, INT-396): MCP servers of its own beside the board's, e.g. a browser for a QA agent, with no hand-written `run`: `"mcp": { "playwright": { "command": "npx", "args": ["@playwright/mcp@latest"], "env": { … } } }`, or `{ "type": "http" | "sse", "url": "https://…", "headers": { … } }`. A name is letters, digits and dashes, and never `intellagent`. The board writes them to `data/agent-mcp/<name>.json` (its runs may not read that folder, since an `env` may hold a key) and the run loads it with `--mcp-config` and allows each server's tools whole (`mcp__<name>`). A hand-written `claude` run gets the same as flags of its own at the end. An agent on probation gets none. Only the human's agents.json sets it: `PATCH /api/agents` can't, and a preset carrying one is refused. A server that doesn't check out is skipped and named in `GET /api/agents` (`error`).
- **A hand-written run that forbids what it meant to allow** is named in `GET /api/agents` (`error`). Claude's `--allowedTools` and `--disallowedTools` each take every value up to the next flag, so tools appended after `--disallowedTools` are forbidden. The check looks for a tool the run also allows, a whole MCP server (`mcp__name`), the board's own CLI and the agent's own `commands`. Move them before `--disallowedTools`, or use `mcp` and `commands`.
- **What the permissions do not stop.** A run built from permissions may not use Claude's file tools on the board's own files: `local.json` (the human's token), `agents.json`, `agent-context/`, the agents' MCP configs (`data/agent-mcp/`), `.git/hooks/` and (for writing) the board's data. `node --test` is allowed only bare, without flags. These are speed bumps for a careless agent, not a wall. **An agent that can edit files and run tests can run any code as you**: it can change a test or the `test` script and run it, and that code can read and change everything you can, including the files above. Until standing agents run as a separate user, don't give agents with edit and test tickets whose content you don't trust (pasted text, web pages, issues from strangers). A custom `run` gets none of these rules.
- **A reviewer that is not Claude:** `"run": "node bin/reviewer-adapter.js"` (with `"reviewer": true`, no `keepAlive`) lets any OpenAI-compatible model review. It reads the prompt on stdin and gets exactly five tools: `read_file` (under the folder reviewed; never `local.json`, `agents.json`, `.git` or `.intellagent`), `git_log`, `git_diff`, `run_tests` (the one command in `INTELLAGENT_ADAPTER_TEST`, run without the key or any token) and `board_call` (a comment, or its verdict, nothing else: only on the tickets the prompt names, at most three comments per run, with every `@` broken so a comment mentions nobody). A run that posts no verdict ends as an error. The URL, model and key come from `INTELLAGENT_ADAPTER_URL`, `…_MODEL` and `…_KEY` (the key in the board's own environment, never in agents.json). It prints a Claude-shaped `result` line with the usage. It runs as the same OS user as the board: the tool list limits the model, not the process (a separate user is INT-248).
- `run`: the command (default `claude -p …`). It gets the events as a prompt on stdin, `INTELLAGENT_AGENT`, `INTELLAGENT_URL` and `INTELLAGENT_EVENTS` (JSON file) in its environment, and runs in the project folder. A `claude` run inherits the board's whole environment; any other command (a custom `run`) inherits only what a shell needs (`PATH`, `HOME`, `TEMP`…) and the names in its `inheritEnv`, so board secrets such as API keys never reach it unless the human lists them. `"env": { "NAME": "value" }` adds a variable and `"NAME": null` removes one, and `"inheritEnv": ["NAME", …]` passes on only those names (plus what a shell needs, such as `PATH`); for a `claude` run it narrows the default, for a custom run it widens it. The board's own `INTELLAGENT_*` variables are always set. A malformed `env` or `inheritEnv` leaves the agent off until it is fixed. On a board with agent tokens it also gets `INTELLAGENT_TOKEN`, its own token (never another agent's or the human's, and never one the board itself was started with), so a run that can't read local.json still calls the board as itself; a rotated token starts a fresh keep-alive session.
- **One run per agent at a time**; events that arrive meanwhile go into the next run.
- **Run logs** (`data/agent-runs/<agent>/`): the newest 20 are always kept, and any younger than 24 hours however many there are, so an agent that runs every few seconds still has the last day to read; at most 2000 per agent. A log and its events file go together.
- **Signs of life:** while a run is going, `GET /api/agents` gives `lastActivityAt` (its last call to the board or output in its log) and `stalled: true` once that is older than `stallMinutes` (default 10; `0` = never). A one-shot run prints nothing until it ends, so a long build or test without board calls also counts as stalled: it is a hint for the human, and nothing is killed. After a run, `lastRun.about` still says which tickets and requests it was woken to answer.
- **What a run is doing:** `now: { since, why, items, line }` per agent while a run is live (`null` otherwise). `line` is the newest of its own status line and the status of a ticket it holds. A run that holds no ticket (triage, reviewing, answering a request) sets its own with `PUT /api/profiles/me/status { status, items? }` (`""` clears; CLI `intellagent do set_activity status="…"`). Only your own line, never another agent's. It emits `agent.activity { agent, line, items }`, which wakes nobody (no recipients; at most one every 2 s per agent), and it ends with the run. `agent.run.started` carries `why`. Each agent keeps `history`, its last 10 runs `{ startedAt, durationMs, code, why, items }`, across restarts; `GET /api/agents?recent=10` adds the 10 newest across all agents.
- A run that fails, times out or is cut off by a restart is **retried automatically** with the same events (the prompt says it was interrupted — check for half-finished work). After `maxFailures` in a row the agent is **flagged failed** and waits for the human, except for **one more try**: `failedRetryMinutes` (default 30; `0` = off) after it failed it gets one probe run with its queued events. A probe that works puts it back to normal; a probe that fails leaves it failed until the human resumes it, with no further probe. `agent.failed` carries `probeAt` (`null` when no probe follows), and `GET /api/agents` shows `probeAt` on a failed agent and `probing` while the probe runs.
- **The usage limit is not a failure.** A run the account's usage limit refused (claude prints a `rate_limit_event` with `status: "rejected"` and `resetsAt`) keeps its events and counts no failure. The agent, and every agent served by the same `provider` (one account, one limit; an agent with no provider alone), waits with status `waiting`, `waitingFor: "usage limit"` and `resumesAt` at the reset, then runs by itself. One `agent.usage_limited { agent, provider, until, agents }` event says so (it wakes nobody). The idle-board alarm stays quiet meanwhile and counts its quiet stretch from the reset.
- **The account's usage.** Every claude run prints how much of the account's windows is spent; the board keeps the newest per provider. `GET /api/agents` → `usage: { <provider>: { window, utilization, resetsAt, windows: { five_hour, seven_day }, heldBack, holdAbove } }`. Above `holdBackAbovePercent` (default 85; one value for the board, set in agents.json `defaults`, a per-agent value is ignored, 0 means 85) of the five-hour window, optional work waits for the reset: **pickup of unassigned tickets and supervise nudges** are not offered, so what is left goes to work already started, reviews, triage and the human's requests. Work an agent had already seen before the hold doesn't wake it again at the reset. `…/metrics` counts the minutes held (`usageHeld: { minutes, prev }`).
- `maxRunsPerHour` (default 20; `null` = no limit) and `throttleMinutes` (default 3; `0` = off): a quiet agent wakes as soon as something arrives, but for `throttleMinutes` after each wake further events wait and arrive together in one run — editing ten tickets in a row wakes it at most twice.
- Each run starts with no memory: **everything worth keeping goes on the card.**
- **Runs end with the board.** If the board dies (a crash, killed from Task Manager), the system ends its runs and everything they started: on Windows a kill-on-close job object (a small helper built once with the .NET Framework's `csc.exe` into the board's data folder), elsewhere the run's process group. A hard end gives a run no time to clean up, so its retry may find a git operation still open. If the helper can't start, runs start as before, the board log says why, and the next board start stops what was left. `INTELLAGENT_RUN_GUARD=off` turns this off.
- **Stop all agents** (Agents page, or `POST /api/agents/stop-all`; human or the `agents.control` grant): kills every run (not counted as a failure; its events stay queued), pauses every standing agent, releases agent leases and an agent's master lease, and moves the tickets they were working on in the working column back to Ready with a ⏹ comment (assignee kept). `POST /api/agents/resume-all` brings them back.
- **Stale work goes back:** a ticket left in the working column with no lease, no running agent and no activity for `staleWorkMinutes` (manifest, default 120; `0` = off) returns to Ready with a ⏸ comment. A person's own tickets are never swept, nor are tickets waiting on the human (an open question or review).
- `intellagent agents` lists them; `agents add|pause|resume|run|log|remove <name>`. `GET /api/agents` shows status, queue and the last run; pause/resume/run are human-only. `intellagent autostart on` starts the board (and so its agents) at login.
- An open-ended master lease ends by itself after `masterIdleMinutes` (manifest, default 120) without activity from its holder, unless the holder is a standing agent mid-run.

Your inbox already includes tickets you created, leased (now or before), commented on, were assigned or @mentioned on — and, while you hold the master lease, every ticket on the board.

### Machine leases: heavy work, rationed
Several agents on one PC can each run a browser, a simulation or a timing run; all at once they run the machine out of processor or graphics-card memory and spoil each other's timings. The **lease program** (`leases-server.js`, one per PC on `127.0.0.1:7499`, shared by every board; state in `~/.intellagent/leases.json`) rations it. Usually a **Guard** agent asks on the others' behalf; any agent may ask directly.
```
intellagent leases ask --holder natasha --cpu 11 --gpu 2048 --minutes 20 --ticket LNZ-3 --purpose "heat solve"
  → { granted: true, lease: { id: "L4", expiresAt … }, floor, ceiling }
  → { granted: false, reason: "no room: 11 threads, 2048 MB of card in use of 12 threads, 8192 MB", freesAt: "…" }
intellagent leases renew L4 --minutes 15      # still at it
intellagent leases done L4                    # finished: free it at once
intellagent leases status | machine           # what is leased (the floor) | what the machine is actually doing
intellagent leases ceiling --cpu 8 --gpu 5000 # the most that may be leased at once (Guard / human)
```
- Ask in **threads** (`cpu`) and **MB of card** (`gpu`); `--exclusive` wants the machine to itself (timing runs) and waits until it is empty.
- A no is not an error: it says why and, where waiting helps, `freesAt`. A request bigger than the ceiling gets `freesAt: null`.
- Every lease **ends by itself** when its time is up (at most 120 minutes; renew to keep it), so a crashed agent never strands the machine. Declare `done` as soon as you are.
- The human's own work never asks: the Guard watches `leases machine` and lowers the ceiling to leave them room.
- `leases machine` also lists the busiest processes with their command lines; `agent: true` marks one started from the board's own folders (a worktree, a review checkout, an agent's build). A test still running after its run ended shows here, holding threads no lease accounts for. `intellagent leases reap <pid>` stops it and its children; it refuses any process not marked `agent` (`403 NOT_AGENTS`), so the person's programs are out of reach. Processes are listed, and reaped, on Windows only for now: elsewhere reap answers `501 UNSUPPORTED`.
- HTTP for other tools: `GET /status`, `GET /machine`, `POST /ask`, `POST /leases/<id>/renew|done`, `PUT /ceiling`. Only programs on this PC: the Host must be `127.0.0.1:7499` or `localhost:7499`, a request with an `Origin` header (a web page) is refused, and writes need `content-type: application/json`. Errors are `{ error, code, hint }`. The CLI starts the program when it is not running; `intellagent leases start|stop` by hand.

## 5. Events — know when things change

Every change emits an event with an increasing `seq` (the log, `events.jsonl`, is set aside once it passes `eventsMaxMB`, default 20, and only the newest `eventsKeep`, default 5, are kept; `seq` carries on). Each event lists `recipients`: the leaseholder and past leaseholders, whoever asked for help, the agent author, the assignee, thread participants, the master-lease holder and @mentions. **`for=<your-name>` is your inbox.**

```
GET /api/events/wait?since=<seq>&for=my-agent&timeout=25     ← long-poll: returns as soon as something matches
GET /api/events?since=<seq>&board=main&types=item.created     ← immediate, for catching up
GET /api/stream?board=main&agent=my-agent                     ← Server-Sent Events (curl -N)
```

Response: `{ "events": [...], "cursor": 812 }` → pass `cursor` as `since` next time.

Filter keys (all optional, AND-ed): `board`, `types` (comma list, `lease.*` wildcard), `itemId`, `column` (destination column), `claimant`, `for`, `itemType`, `parent`, `fields` (changed fields, e.g. `priority,properties.risk`; `properties` = any property), `actorKind`, `excludeActor` (skip your own echoes).

**Durable subscriptions** keep the cursor for you — the simplest loop:

```
POST /api/subscriptions                 { "label": "my inbox", "filter": { "for": "my-agent" } }  → { "id": "sub_…" }
GET  /api/subscriptions/sub_…/next?timeout=25    → new events since last call (advances the cursor)
```

A subscription is its creator's: only they (or the human) may delete it, ack it or read it without `peek` (`403 FORBIDDEN` otherwise). Anyone may read it with `?peek=true`, which moves nothing.

Typical recipes:

| Want | Filter |
|---|---|
| New tickets landing in Ready | `types=item.created,item.moved&column=Ready` |
| Anything touching my tickets | `for=my-agent` |
| Priority or risk changes | `fields=priority,properties.risk` |
| All spikes | `itemType=spike` |
| My lease warnings | `types=lease.*&claimant=my-agent` |
| Handed to me | `types=item.assigned,item.unblocked&for=my-agent` |
| What another agent did | `actor=other-agent` (add `tail=true` on `/api/events` for the newest) |

### Safe retries
- **`Idempotency-Key: <anything unique>`** on a write: repeating it (same caller, same key, within 24h) returns the first reply with `Idempotent-Replayed: true` instead of acting twice. Inside a standing-agent run, `intellagent api` and the MCP tools add one automatically, derived from the event batch — so a retried run that repeats an identical write doesn't duplicate it.
- **`X-Intellagent-Run: <id>`** tags every event a call causes (`actor.run`); filter with `?run=<id>`. Standing agents set it (`INTELLAGENT_RUN`), and a retried run's prompt lists what the failed attempt already did.
- **Subscriptions, at-least-once:** read with `GET /api/subscriptions/<id>/next?peek=true`, handle the events, then `POST /api/subscriptions/<id>/ack { "cursor": … }`. Without `peek`, `next` advances immediately (at-most-once).

### Permissions & tokens
The manifest may restrict agents (`permissions: { "<name>" | "*": { "columns": ["Backlog","Ready"], "readOnly": false } }`) and require tokens (`auth.agentTokens`). Check yours with `GET /api/permissions/me`; send tokens as `Authorization: Bearer <token>`. The human's own token (from `intellagent init`) lives in `.intellagent/local.json`; without it, requests sending `X-User` are refused, so agents cannot act as the human. A board made before tokens existed gets one with `intellagent token` (then restart the board and `intellagent open` to sign in; `--rotate` replaces it). **Sign-in link:** `intellagent open` and `intellagent init` print the link they open (`<url>/#token=…`, the human's own token, so only the human runs them; an agent is refused with `HUMAN_ONLY`). `intellagent open --print` prints it and opens no browser, for handing someone access. The page removes the fragment from the address bar at once, so copy the link from the terminal.

### Git
`node intellagent/git-hook.js install` links commits that mention `INT-12` to that ticket. `node intellagent/git-hook.js sync-ci` fills a `ci` field from GitHub checks for tickets with a `pr` URL (needs `gh`).

```
GET  /api/search?board=main&q=login&type=issue&prop.risk=high&prop.score=gte:3&claimant=exists:true
POST /api/search  { "board": "main", "q": "token", "where": { "properties.risk": "high",
                    "priority": { "in": ["High","Critical"] }, "blockedBy": { "exists": true } },
                    "sort": "priority", "order": "desc", "includeArchived": true, "full": false }
```

## 7. Boards, columns, white-label

```
POST  /api/boards                         { "name": "Refactor", "idPrefix": "REF", "template": "default|simple|empty" }
POST  /api/boards/main/columns            { "name": "QA", "color": "#f2a541", "icon": "eye", "position": 3,
                                            "flags": { "allowCreate": false, "wipLimit": 3 } }
PATCH /api/boards/main/columns/QA         { "flags": { "allowCreate": true } }
PUT   /api/boards/main/directives         { "directives": "markdown" }
PATCH /api/app                            { "name": "Acme Ops" }
GET   /api/app                            → also runningCommit, runningSince, mainCommit, behind, behindCommits, behindTickets
POST  /api/app/restart                    (human only) restart onto the code on main; never happens by itself
GET   /api/presence                       → who is connected, their leases and subscriptions
```

The human edits columns in Settings › Columns (rename, colour, icon, flags, order, add; delete only when empty). Custom flags are stored as-is; `pickup` and `working` tell agents where work starts and happens.

**How the board is governed is the human's.** Unless the human granted the matching Board admin power (see *Grants*), agents get `403 HUMAN_ONLY` for adding, deleting or reordering columns, changing a column's known flags (`allowCreate`, `allowMoveIn/Out`, `wipLimit`, `releaseLeaseOnEnter`, `autoArchiveAfterDays`, `humanOnlyIn/Out`, `review`, `sleeping`, `pickup`, `working`), choosing the `coordinator`, changing the board rules (`directives`) and the built-in field settings (`PUT …/schema { builtins }`). A column's name, colour, icon and other custom flags, and declared fields, stay open to agents. Renaming the app (`PATCH /api/app`) and adding a board (`POST /api/boards`) are the human's too. To change the rest, ask on a card. A read-only agent may still comment, ask and keep its own profile, memory and subscriptions, and nothing more: holding `agents.control` or `agents.manage` doesn't change that.

### Presets: a package for a kind of team
A preset is a folder with `preset.json` (`name`, `version`, `extends?`, `board`: columns, schema fields, ticket templates, directives). The built-in templates (`intellagent templates`) are presets at version 1; `stories` ships with the package as a second one that has nothing to do with code. A preset may also carry a **team** (below); grants and commands are never installed from one. It is the **human's** to install, in the CLI (`403 HUMAN_ONLY` for an agent, except `preset list`; that check is a speed bump, not a wall: the CLI trusts `INTELLAGENT_AGENT`, and an agent that can edit files and run commands can reach the human's token in `local.json` anyway, see "What the permissions do not stop"):

```
intellagent preset list                        what exists (built-in, shipped, added) and what this board has installed
intellagent init --preset software|stories|<folder> [--yes]     a new board from a preset
intellagent preset add <name|folder> [--yes]   add one to a board that exists
intellagent preset diff <name|folder>          what a newer version would change, piece by piece
intellagent preset update <name|folder> --accept all|id,id
intellagent preset export <folder> [--name N] [--version V] [--force]   write this board as a preset (human only)
```
- `preset export` writes `<folder>/preset.json` from the live board: columns and flags, fields, built-in field settings, ticket templates and directives. It leaves out, and prints, everything else: tickets, ids, tokens, `local.json`, `agents.json` (run commands, env, MCP configs), the board's data, card rules and the idle-alarm setting (a preset cannot install them yet) and the team (roles, agents, context, grants: not built yet). An absolute path in the text becomes `<path>` and a ticket template's parent is dropped, each reported. It refuses to replace a `preset.json` without `--force` (`409 CONFLICT`).
- **A team in a preset** (`preset.json` → `team`: `{ roles, slots, base }`). `roles` are the human's own roles (`label`, `brief`, `perms`, `model`…, the same as agents.json `roles`). `slots` are places for agents, not agents: each has a lowercase key and `role` (required), and may set `model`, `provider`, `description`, `areas`, `concerns`, `listen`, `pickup`, `reviewer`, `supervise`, `keepAlive`, `idleAlarm`, `context` (`"agent-context/<slot>.md"`, a file in the preset folder, at most 8000 characters, never a link out of it or a non-regular file) and `grants` (proposals). `base` is `"base-context.md"`, a file in the folder. `run`, `env`, `inheritEnv`, `commands` and MCP config are **refused anywhere in a team** (`BAD_PRESET`): a preset never brings machine-specific or dangerous config. The CLI installs through `POST/PATCH /api/agents`, never by writing agents.json.
  - Name the slots at install: `intellagent preset add <folder> --agents lead=rocket,builder=groot` (a slot with no name is skipped and listed). Each becomes a **new agent on probation** (it runs nothing until you `agents accept` it); a name that already exists is refused (`409`). The prompt lists every role, slot, model, setting and the opening lines of each context page.
  - **Grants are proposals.** The prompt asks per grant, with its whole scope (`where`, `minOks`, `from`); `--yes` writes none unless `--grants` is also given. Update and diff only report that a proposal changed; nothing writes a grant.
  - **The base context** teaches every agent on the board, so it is installed only on its own yes (asked separately) or `--base`; `--yes` alone leaves it. `preset update --accept all` leaves it out too unless `--base` (or name it: `--accept base`). Your own edited base is never overwritten.
  - `preset diff` / `update` treat each role, slot, context page and the base as a piece (`slot:<slot>`, `context:<slot>`, `base`) with the never-overwrite-edited rule. Note that an update can change an accepted agent's role, pickup or keepAlive if the preset's slot changed and you had not edited it.
- Installing first lists what the preset gives power over (human-only columns, read-only fields, board rules, and commands or tools once presets carry them) and asks; `--yes` agrees up front, and with no terminal and no `--yes` it refuses with `400 BAD_REQUEST`. Nothing is fetched again later: a folder is copied to `<board folder>/presets/<name>/`.
- `<board folder>/presets.json` records, per preset, its version and the value of each piece it installed. A piece is `column:<name>`, `builtin:<key>` (a built-in field's settings, e.g. a relabelled `type`; a board always has one, so it is offered as `new` the first time), `field:<key>`, `ticket-template:<key>` or `directives`. The prompt before an install lists every column flag and built-in field setting the preset sets. `preset diff` of an installed, unchanged preset says it is up to date. An update compares the board, what was installed and the new version: `new` and `update` can be accepted; `edited` (you changed it, or it was there before) is **never overwritten**; `dropped` (you removed it) and `gone` (no longer in the preset) are left alone.
- `add` only adds what is missing. Presets in `presets/` of the package, or added to the board, are also board templates (`GET /api/templates`, `"template"` in `POST /api/boards`).

## 8. MCP, CLI and the agent skill

Agents reach the board three ways; pick the lightest that works:
- **MCP core** — `node intellagent/mcp.js` lists ten tools by default (`get_briefing`, `get_my_work`, `get_item`, `start_work`, `set_status`, `add_comment`, `ask_human`, `request_review`, `wait_for_events`, `finish_session`; plus `introduce_yourself` until the agent has a role): ~4.5k characters of tool definitions instead of ~21k. `INTELLAGENT_MCP_PROFILE=full` (or `--profile full`) lists all 57; `INTELLAGENT_MCP_TOOLS=name,name` lists your own set. Every tool stays callable by name in every profile.
- **CLI** — `intellagent do <operation> key=value …` runs any of those operations by name (same parameters as the MCP tools); `intellagent help <operation>` prints its exact request (`intellagent help <command>`, e.g. `help init`, prints a command's usage); `intellagent api <METHOD> <path> key=value …` calls any route. Output is JSON; on an error the reply stays on stdout and `error <status> <CODE>: <message> — hint: <hint>` goes to stderr with exit 1 (2: board unreachable or bad input, 3: no board). It never prompts; `INTELLAGENT_AGENT` sets who you are.
- **Skill** — `skills/intellagent/SKILL.md` (`intellagent skill install`) teaches the day-to-day loop and the CLI for everything beyond the core; it loads only when the agent works a ticket.

A narrow Claude Code permission rule for agents: `Bash(intellagent *)` plus the core tools by name (`mcp__intellagent__get_briefing`, …). `mcp__intellagent` alone allows whatever the server lists.

**A board kept outside the project:** set `projectRoot` in its manifest (`intellagent init --project <path>`, or `intellagent project <path>` on an existing board, then restart). Standing agents then run in that folder (worktrees are kept in the board's folder), the project's CLAUDE.md and git are read from there, and every brief names the folder. In the project, `intellagent link <board folder>` lets the CLI, MCP tools and the agents you start there find the board (`.intellagent/link.json`, git-ignored); `intellagent status` shows the project folder.

**A board of your own to try things on (sandbox).** `intellagent sandbox <you>` starts a throwaway board just for you, on a port that stays yours (7431, 7432, …), and prints its address and a sign-in link for its own human. `--from main | <agent> | <folder>` picks the code it runs — main, an agent's worktree (yours, to see your branch working, or the author's, to review it) or any checkout; `--seed board | demo | empty | snapshot` what it starts with (`board`, the default when the real board has data, copies the board `init` set up — columns, fields, ticket templates, rules, id prefix — with no tickets, and the output names that board; `snapshot` copies the real board's tickets: for reproducing what the human saw); `--fresh` wipes it. Run it again after changing code to restart it; its data stays. `sandbox list`, `sandbox stop <you> | --all` (it stops whichever process holds the sandbox's port, as long as the board there says it is a sandbox, even when its `server.pid` is missing or stale). **Stop says why:** `stop` prints `stopped`, `not running` (nothing answers on the port) or `STILL RUNNING — <reason>` with the port (the board there is not a sandbox, no process holds the port, the process could not be killed, or the port stayed taken), and exits 1 unless the sandbox is gone; `--json` gives `{ name, port, stopped, code, reason }`. **Unused sandboxes stop themselves:** a sandbox that has had no request for `sandboxIdleHours` (default 4; `--idle-hours N` on start; the liveness poll of `GET /api/app` does not count, and an open stream does: a tab on the board or `intellagent wait` keeps it up; `--idle-hours` takes a number, 0 = never) exits and leaves `data/stopped.json`, which `sandbox list` shows (`stopped: idle for 4 h`). `--keep` exempts one (`sandboxKeep` in its manifest; a restart keeps both settings). When all 200 ports are taken, starting a new sandbox takes the port of the one stopped longest (over a minute ago, with a `stopped.json`; its data stays, it gets a new port when started again, and it leaves `sandbox list`). Talk to it with `--url <its address>` on any command (or `INTELLAGENT_URL`); `--as <name>` sets who you are there (or `INTELLAGENT_AGENT`). It is named for you ("Nebula's Board", in the header and as the board's name, even when seeded from a snapshot), so it is never mistaken for the real board. It is safe by construction: standing agents never run on a sandbox (`sandbox: true` in its manifest), its sign-in token is its own, and nothing you do there reaches the real board. It lives in `sandboxes/<you>/` beside the real board's manifest (git-ignored).

**Trying the author's CLI (review).** `intellagent sandbox exec <name> -- <command…>` runs `bin/intellagent.js` *of the code that sandbox runs* (`sandbox <name> --from <author>`), on that sandbox's board and as its human, e.g. `intellagent sandbox exec nebula -- preset add ./x --yes`. Output and exit code come back unchanged. It needs no shell permission beyond `intellagent *`, but an agent needs the **Run an author's code** permission (`run-authors-code`; the Reviewer role holds it): the board says in `GET /api/permissions/me` (`runAuthorsCode`, and `runAuthorsCodeWhy` / `runAuthorsCodeHint` when false) and without it the CLI exits 1 with `403 NO_PERMISSION`. It cannot reach another board: no `INTELLAGENT_*` of yours is passed on (so never the real board's URL or token), `--url`, `--as` and `--manifest` are refused (`403 FORBIDDEN`), and so are `start`, `stop`, `merge`, `autostart`, `token`, `hook`, `skill`, `link`, `project`, `sandbox`, `watch`, `mcp` and `leases`; `init` only in the temp folder, never started. A sandbox that is not running answers `404 NOT_FOUND` with the command to start it. Put `--` before the command: flags after it belong to the command. **It is still the author's code running as you:** it gets your other environment variables (API keys included) and your files, as running their tests does. Only for a ticket you are reviewing.

Shell tips: the CLI finds this project's board by itself (nearest `.intellagent/`), or set `INTELLAGENT_URL`. key=value nests on dots (`fields.risk=low`) and parses JSON values; pass a JSON body as one argument, `@file.json` or `-` for stdin. **One long value from a file:** `key=@path` reads that value from the file as text (`intellagent api POST …/comments body=@C:/tmp/review.md`; the same in `intellagent do`), and `key=@@text` sends the text `@text`. The file must be in the project, its worktrees or the temp folder, and never `local.json` or the board's data (exit 2 with a code and hint otherwise). A word after `@` that is not a file stays text, so `body="@rocket take this"` still mentions rocket. A comment or verdict whose whole text is a file path is saved as written, but the reply has a `warning`: the board does not read files named in a comment. Windows PowerShell: use `curl.exe`, not `curl`; prefer the CLI.

### Agent tokens
A board may require every agent to send a token (`auth.requireAgentTokens` in the manifest; **new boards from `intellagent init` turn it on**, existing boards are unchanged). Tokens live in `.intellagent/local.json` (git-ignored), and the CLI and MCP tools in the project send the right one by themselves. The human issues one with `intellagent token --agent <name>` (`--rotate` replaces it; the board accepts it at once); standing agents get one automatically. An agent elsewhere passes `INTELLAGENT_TOKEN`. Without one: `401` with a hint naming that command. The board stays on 127.0.0.1 unless you change `host`. It answers only to its own names (`127.0.0.1`, `localhost`, the `host` it is bound to; `allowedHosts` in the manifest adds more, e.g. a proxy): any other Host gets `403 BAD_HOST`, so a web page that rebinds its name to this PC can't reach it. Writes from a browser must be `application/json`. Big replies are gzipped for clients that aren't on this PC (`compress` in the manifest: `remote`, the default, `always` or `never`); on this PC compressing only makes them slower.

## 9. Setting up a board in a project

Asked to "set up Intellagent here"? Use the **intellagent-setup** skill (`skills/intellagent-setup/SKILL.md`). It first asks what the board is for (kind of work, team size, how hands-off), then stops and asks the human at each checkpoint (template and prefix, the proposed fields and rules, a recommended team with reasons, the seed tickets, and the features as choices with a recommended setting each; nothing is switched on without a yes) and only touches `.intellagent/`, `.mcp.json`, `CLAUDE.md` and `.git/hooks/`, and only the ones the human agreed to. The commands it uses: `intellagent init --template <t> --name "…" --prefix XX` (or `--preset <name|folder>` instead, after showing the human the powers it lists), `intellagent preset list`, `intellagent templates`, `intellagent status`, `intellagent hook install`, `intellagent autostart on`.
